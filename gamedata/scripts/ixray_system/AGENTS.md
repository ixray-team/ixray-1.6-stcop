# Системный глобальный Lua-слой

Родительская карта: [скрипты](../AGENTS.md). Архитектура сервисов: [Framework](../ixr_framework/AGENTS.md). Контракты модулей: [modules](../ixr_framework/modules/AGENTS.md). Контекстные логи: [public_components](../ixr_framework/public_components/AGENTS.md).

Эта папка содержит системные `.lua`, загружаемые движком в глобальное окружение. Они не являются обычными `.script`-модулями Framework и не подключаются через его список управляемых модулей. Изучение этих файлов не является запросом на изменение отладчика или глобального API.

## Загрузка движком

В исходниках движка смотри `IX-RAY/src/xrScripts/lua_ext.cpp`, функции `lua_init_ext` и `LoadScriptToGlobal`.

1. Движок открывает используемые Lua-расширения.
2. `LoadScriptToGlobal` находит файл под `$game_scripts$/ixray_system/`, компилирует и выполняет его в глобальном окружении; возвращает признак успешной загрузки.
3. В `lua_init_ext` сначала загружается `global.lua`, затем `dynamic_callbacks.lua`.
4. Открывается native-библиотека `socket.core`, затем загружается `socket.lua`.
5. При успешной загрузке socket-скрипта вызывается `pdebug_init` и загружается `LuaPanda.lua`.

Это этап подготовки Lua-состояния. Последующий запуск Framework после загрузки локации проходит через ALife `start_game_callback`, а не через регистрацию этих `.lua` в автозагрузчике.

## Карта файлов

| Файл | Ответственность |
| --- | --- |
| `global.lua` | Настройки совместимости Lua/JIT, подключение отладчика, глобальные обёртки Framework, профилирование, логирование и общие исторические функции. |
| `dynamic_callbacks.lua` | Глобальный контракт регистрации/отправки событий и перенаправление в `ixr_signals`; локальный fallback для предусмотренных исходных intercepts. |
| `socket.lua` | LuaSocket helper над `socket.core`: `connect4`, `connect6`, `bind`, `choose`, source/sink. Возвращает таблицу socket API. |
| `LuaPanda.lua` | Сторонняя Lua-часть отладчика LuaPanda с исходным уведомлением о BSD 3-Clause лицензии; взаимодействует с native-частью движка и VSCode. |

## `global.lua`: публичные семейства

Для игровых скриптов вне `ixr_framework/` публичная граница — глобальные методы этого `global.lua`, глобальные функции `dynamic_callbacks.lua` и данные/API, явно предоставленные обратными вызовами (аргументы и предусмотренные результаты). Сами эти системные файлы делегируют внутрь Framework, но внешний потребитель не должен копировать их внутренние вызовы `ixr_framework.get_module`, обращаться к `get_framework`, `_G` или приватным таблицам для обхода глобального API. Предпочитай готовые сервисные обёртки; `GetModule`, `IsModuleLoaded` и `ClosureModuleIsExists` принимают только alias, когда такой доступ действительно предусмотрен контрактом.

- Инициализация: `ixr_on_start_game_callback` сначала вызывает `_G.start_game_callback()`, затем `ixr_framework.init()`. Настройка входа — `../../configs/alife.ltx`, секция `[alife]`, `start_game_callback = ixr_on_start_game_callback`.
- Модули: `IsModuleLoaded`, `GetModule`, `ClosureModuleIsExists` делегируют в `ixr_framework`. В игровом коде все эти вызовы принимают только alias (`"ixr_timers"`), не имя файла реализации (`"ixr_module_timers"`). Прямой доступ к неймспейсу управляемого модуля или через `_G` категорически запрещён. Глобальные сервисные обёртки также должны обращаться к модулям по alias.
- Сохраняемые данные: `HasStorageVar`/`GetStorageVar`/`SetStorageVar`/`UnsetStorageVar`, объектные варианты `*StorageObjectVar` и общие `*StorageSharedVar`. Скриптовые и объектные обёртки используют caller context; shared-обёртки используют общую ячейку.
- Реестр в памяти: `HasRegistryValue`, `GetRegistryValue`, `SetRegistryValue`, `UnsetRegistryValue`.
- Таймеры: `TimerCreate`, `TimerCreateWithNextFreeName`, `IsTimerExists`, `TimerPlay`, `TimerStop`, `TimerDelete`. Прежде всего для сюжетных игровых действий с сохраняемым состоянием; не используй недешёвое сохранение таймеров ради обычной отсечки служебного update.
- Триггеры: `TriggerCreate`, `TriggerExists`, `TriggerRemove`. Для геймплейных/сюжетных пространственных зон, а не произвольных внутренних проверок скриптов.
- Опции: `HasOptionsVar`, `GetOptionsVar`, `SetOptionsVar`, `SetOptionVisible` и метаданные страницы `SetOption*`.
- Ограничение частоты: `IsActionThrottled`, `IsNotActionThrottled`. Сохраняй противоположный смысл этих двух результатов.
- Логи: `IXRLogUseFileLog`, `IXRLogUseConsoleLog`, `IXRLogUseTimeInLog`, `IXRLog`, `IXRLogEmptyLine`, `IXRLogClear`; реализация — `ixr_logs`. Файлы контекстных логов находятся в `$logs$/ixr_framework_logs/__log__<источник>.txt`.
- Tracy: `PROF_EVENT_BEGIN`, `PROF_EVENT_END`, `PROF_EVENT_CLOSURE`; реализация — `ixr_tracy_profiler`. Callable должен выполняться и без подключённого профайлера.
- Отладчик: `DebuggerMode`, `debug_jit_off`, `debug_jit_on`, `debugger_attach`. Вход отладки использует LuaPanda на `127.0.0.1:8818`; не запускай его просто для чтения карты.
- В начале файла уже есть `jit.opt.start(2)`, `string.gfind = string.gmatch`, `math.mod = math.fmod`. Не меняй режим JIT и глобальные алиасы в рамках посторонней задачи.

При изменении обёртки сверяй сигнатуру и результаты с соответствующим модулем. Caller-based области Storage/Options/Logs зависят от стека: дополнительная функция может изменить владельца данных и имя журнала.

## `dynamic_callbacks.lua`: глобальный контракт событий

Отправка события не гарантирует наличие подписчиков. Для интеграций аддонов стандартная логика обязана продолжаться без их ответа: исходные значения и ветки сохраняются, обязательного ожидания аддона не появляется. Отключение или удаление аддона не должно блокировать ванильный код.

- Публичные функции: `AddIntercept`, `RemoveIntercept`, `RegisterScriptCallback`, `UnregisterScriptCallback`, `SendScriptCallback`; алиасы совместимости — `callback_set`, `callback_unset`, `make_callback`.
- При доступном Framework и зарегистрированном `ixr_signals` вызовы делегируются соответствующему модулю. Локальная таблица `intercepts` содержит fallback для `save`, `load`, `update`, `save_state`, `load_state`; это не замена полного каталога Framework.
- Подписчик — функция либо объект с методом события. В fallback функция вызывается с `...`, объект — с собственным `self` и `...`. Сохраняй аргументы и алиасы совместимости.
- Новые имена коллбеков регистрируются **только** в `../__ixr_override_signals_intercepts.script`. Не добавляй новые события в локальную fallback-таблицу или в эти глобальные обёртки.
- Обозначения аргументов в `../__ixr_override_signals_intercepts.script` предназначены для переноса мододелом в сигнатуру обработчика. Сохраняется порядок; имена могут описывать роль и применение вместо реального типа. Эти строки не участвуют в связывании параметров или проверке типов.
- Подписка и отправка различаются: существующие глобалки доступны пользователям, но каталог проекта расширяется через отдельный override-файл.
- При анализе не вызывай эти функции для проверки наличия Framework: они могут инициировать доступ к модулям и изменить состояние игры.

`RegisterScriptCallback`/`SendScriptCallback` также обеспечивают интеграционные обвязки аддонов: подписчик меняет общий контекст или передаёт функцию-замену, исходный код после отправки использует результат. Это не возврат значения из шины и не автоматическая подмена функции. Пример и правила находятся в [корневой карте скриптов](../AGENTS.md).

## Сторонние зависимости и границы изменений

- LuaPanda и LuaSocket сохраняют свои исходные API и лицензионные заголовки. Не переписывай их ради единого стиля проекта и не меняй версии в рамках описания карты.
- Socket API зависит от native `socket.core`; LuaPanda — от socket и движковой части. Наличие `.lua` не означает, что достаточно подключить его отдельно из обычного скрипта.
- Отладчик умеет исследовать активные локалки и захваты через debug API, но это не означает доступ к любой лексической переменной произвольного завершившегося скрипта.
- Не подключай отладчик, не открывай соединения и не отключай JIT для изучения структуры. Проверки документации — существование файлов и корректность ссылок; рабочие журналы и конфиги не изменяются.
