# Производные и новые события

Общие правила: [корень Framework](../AGENTS.md). Контракт шины: [модули](../modules/AGENTS.md).

Эта папка расширяет систему событий: объединяет несколько источников с ожиданием их частей либо формирует новое событие из доступных данных. Это не реестр управляемых модулей.

## Пользовательская документация и примеры

- [Контракт сигналов и примеры событий](../../../../IX-RAY/docs/docs/main/ru/scripting/ixr-framework/modules/ixr_signals.md)

Начинай с документации нужного API и примеров, затем сверяй сигнатуры, значения и жизненный цикл с текущей реализацией. Если старая формулировка расходится с актуальными правилами владельца проекта (например, допускает имя файла модуля вместо alias), соблюдай актуальные правила из родительских AGENTS.md. Само обнаружение расхождения не является задачей на изменение скриптов или документации. Минимальную версию проверяй на конкретной странице.

## Карта скриптов

| Скрипт | Источники и результат |
| --- | --- |
| `ixr_callback__actor_on_spawn.script` | На `actor_on_update` ждёт живой `db.actor`, отправляет `actor_on_spawn`, защищает отправку флагом `actor_loaded`. |
| `ixr_callback__on_game_present.script` | Объединяет `actor_on_spawn` и `on_load_screen_await_any_key_pressed` с учётом режима загрузочного экрана; отправляет `on_game_present`. |
| `ixr_callback__torch_enable_disable.script` | Раз в 250 мс проверяет фонарь, отправляет `actor_on_torch_enabled`/`actor_on_torch_disabled`; объект может быть `nil`. |
| `ixr_callback__item_extend_description.script` | После готовности актора обрабатывает фокус предмета, отправляет `on_item_draw_description` с таблицей результата и применяет объединённое описание. |

## Правила расширения

- Новые имена коллбеков регистрируй **только** в `../../__ixr_override_signals_intercepts.script`. В компоненте оставляй подписки на источники через `RegisterScriptCallback` и отправку через `SendScriptCallback`.
- Подписки устанавливаются в `on_game_start`; обработчики update не должны заново регистрировать события или подписчиков.
- Для составного события учитывай любой порядок исходных уведомлений: сохраняй необходимые флаги и проверяй совокупное условие после прихода каждой части.
- Явно определяй нужную кратность отправки и сброс состояния. У `on_game_present` сейчас нет отдельного флага «уже отправлено»: не обещай строго однократное событие только по его имени.
- Начальная синхронизация фонаря также может отправить уведомление. Сохраняй интервал опроса и поддержку отсутствующего предмета.
- Таблица расширения описания является общим изменяемым результатом. Не подменяй её копией и не сортируй подписчиков ради порядка описания: порядок результата задают ключи/готовые утилиты сортировки и объединения.
- Не создавай циклы событий и синхронную рекурсию через обратную отправку исходного события.
- Проверяй новую игру, загрузку сохранения, отсутствие актора, режим без ожидания клавиши и повторный приход источников. Частые обработчики не должны писать подробный лог на каждом тике.

Интеграционные точки `SendScriptCallback` внутри ванильных функций также используют шину, но не обязаны находиться в этой папке. Здесь формируются производные события; в игровом исходнике точка может расширять конкретный шаг вычисления или заменять ветку через переданный контекст. Не переноси такие места автоматически в `extend_callbacks`. Пример обвязки аддона — [корневая карта скриптов](../../AGENTS.md).
