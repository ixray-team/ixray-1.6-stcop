# IX-Ray Lua Framework

Эти инструкции относятся к `ixr_framework/` и вложенным папкам. Сохраняй существующие публичные контракты: ими пользуются фреймворк, оригинальные игровые скрипты и моды. Сначала прочитай эту карту, затем инструкции нужной папки. Для полного обзора пройди все ссылки ниже; вложенные инструкции уточняют общие правила.


Эта документация служит картой существующей реализации для ИИ-агентов. Само изучение структуры не является задачей на исправление или переработку скриптов.

Родительская карта: [все скрипты](../AGENTS.md). Глобальный системный слой: [ixray_system](../ixray_system/AGENTS.md).

## Предпочтительный способ расширения

Сервисы выбираются по назначению: `ixr_timers` — прежде всего сюжетные отложенные действия с сохраняемым состоянием, `ixr_triggers` — геймплейные пространственные события. Система сохранения таймеров недешёвая; не используй её как стандартную техническую отсечку в служебном коде. Для ограничения частоты внутри существующего update обычно достаточно `IsActionThrottled`.

Чтобы вклинить дополнительный вызов аддона, оставляй в общей функции событие со всеми необходимыми аргументами, а код — в подписчике отдельного скрипта аддона. Не добавляй в общий исходник прямые вызовы конкретного аддона и не требуй от подписчика доступа к приватному состоянию. Переданный контекст должен быть достаточен для инкапсуляции правки; без подписчика стандартная работа продолжается.

**Для интеграционных точек обязательна независимость ванили от аддона:** без подписчика, после отключения или удаления аддона общий код продолжает исходное поведение. До события задавай стандартные значения; при отсутствии опционального функтора выполняй исходную ветку. Не вводи ожидание ответа/события/готовности аддона, без которых ванильная операция не может завершиться.

Callbacks являются и точками внедрения поведения. Обвязка аддона может изменить переданную по ссылке таблицу контекста, установить функцию вместо стандартной ветки или выполнить дополнительный код. Общая ванильная база хранит небольшую нейтральную точку `SendScriptCallback`, специфическая реализация — в отдельном скрипте аддона. Реальный пример изменения цены и карта существующих интеграций находятся в [родительской карте скриптов](../AGENTS.md). Это публичное расширение, которое не требует модифицировать ядро Framework.

Пользовательский справочник уже существует: 37 страниц в `IX-RAY/docs/docs/main/ru/scripting/ixr-framework` охватывают обзор, модули, компоненты, утилиты и библиотеки. AGENTS.md — карта для ИИ, а не замена и не параллельная копия справочника. Для нового потребителя начинай с документированного примера и готового публичного API.


Существующий код Framework менять не рекомендуется. Для прикладной задачи сначала используй публичные глобальные методы, API обратных вызовов и события. Новую отдельную ответственность оформляй управляемым модулем и подключай через `__ixr_override_framework_load_sub_modules.script`. Ещё один способ расширения — новое событие с регистрацией в предназначенном для этого публичном файле `../__ixr_override_signals_intercepts.script`.

Если выбранное решение требует переписывания существующего модуля, компонента, глобальной обёртки или внутреннего контракта, пересмотри подход: вероятнее всего, нужен новый модуль, новое событие с регистрацией в `../__ixr_override_signals_intercepts.script` либо выбрано неверное решение. Правка самого Framework уместна для обоснованной задачи на его развитие/исправление, когда существующих точек расширения недостаточно; объясни эту необходимость и сохраняй минимальный объём изменений. Это не отдельный обязательный запрос разрешения при уже поставленной пользователем задаче.

## Архитектура и выбор места для изменений

| Путь | Назначение |
| --- | --- |
| `ixr_framework.script` | Точка входа `init`, реестр модулей, регистрация и вызов их инициализации, доступ игрового кода только через alias. Запускается через ALife callback после оригинальной инициализации. |
| `modules/` | Все управляемые модули: контракт `get_module_info()`, alias, регистрация и отдельная инициализация. |
| `public_components/` | Публичные компоненты-помощники для разработчиков модов. Не требуют регистрации и инициализации через менеджер модулей. |
| `system_components/` | Узконаправленные внутренние компоненты фреймворка и оригинальных игровых скриптов. |
| `extend_callbacks/` | Производные события: объединение нескольких исходных событий с ожиданием условий либо формирование нового события. |
| `ixray_options/` | Настройки самого проекта IX-Ray, которыми управляет команда. Это не шаблоны настроек для модов. |
| `utils/` | Общее публичное API: готовые решения для повторного использования во фреймворке, оригинальных скриптах и модах. Общую логику держи здесь, не копируй по вызывающим скриптам. |

Внутри Framework компоненты и утилиты доступны через неймспейсы своих скриптов; внешний игровой код соблюдает публичные границы, описанные в родительской карте. Не добавляй им `get_module_info` и регистрацию в менеджере только ради использования готовой функции. Отсутствие модульной инициализации не запрещает служебные точки входа: например, у `ixr_tracy_profiler` есть `on_game_start`.

## Связанные точки входа и пользовательские настройки

Пути ниже заданы относительно этой папки. Движковая настройка запуска находится в `../../configs/alife.ltx`: секция `[alife]`, `start_game_callback = ixr_on_start_game_callback`.

| Файл | Что проверять при изменениях |
| --- | --- |
| `../ixray_system/global.lua` | Глобальные обёртки: `GetModule`, `IsModuleLoaded`, `ClosureModuleIsExists`, семейства Storage, Registry, Timer, Trigger, Options, throttling, логирование и профилирование. |
| `../ixray_system/dynamic_callbacks.lua` | Глобальный доступ к сигналам: `AddIntercept`, `RemoveIntercept`, `RegisterScriptCallback`, `UnregisterScriptCallback`, `SendScriptCallback` и алиасы совместимости. При загруженном `ixr_signals` вызовы перенаправляются в модуль. |
| `../___ixr_engine_callbacks.script` | Мост движковых вызовов в Lua, включая `on_frame`. В ряде методов результат возвращается движку через изменяемую таблицу `flags`, которую заполняют подписчики. |
| `../__ixr_override_framework_load_sub_modules.script` | Определяет набор и порядок инициализации модулей через `configure`; мододел может вставить собственный модуль в нужное место списка. |
| `../__ixr_override_autoload_system.script` | Фильтр первичного сканирования: исключает проблемные и ненужные скрипты до проверки их точек входа. |
| `../__ixr_override_signals_intercepts.script` | Единственное место регистрации новых имён коллбеков; публичный справочник позиционных аргументов для мододелов. Строки аргументов — смысловые подсказки, не строгие игровые типы. |
| `../__storage_mod_version.script` | `get_version()` для версии данных хранилища. Само наличие версии не означает автоматическую миграцию или сброс данных. |
| `../example_options/ixr_options_template.script` | Пример пользовательских опций: группы, контроллы, пресеты, видимость, комбобоксы, обработчики. |
| `ixray_options/ixray_global_options.script` | Настройки команды: показ имён переменных опций и `_G.dev_debug`. |

Пользовательские настройки состава модулей, фильтра сканирования и каталога событий находятся в соответствующих `__ixr_override_*`.

- Новые имена коллбеков регистрируй **только** в `../__ixr_override_signals_intercepts.script`. Не добавляй новые регистрации в default-каталог модуля, `dynamic_callbacks.lua`, компоненты или вызывающие игровые скрипты. Отправка и подписка используют готовые глобальные функции.
- Состав и порядок инициализации меняй через `../__ixr_override_framework_load_sub_modules.script`. Это публичная точка расширения, в которой мододел может подключить собственный модуль в нужном месте.
- Первичный фильтр скриптов настраивай через `../__ixr_override_autoload_system.script`. Применяй исключения до обращения к `_G[script_name]` и проверки функции: обращение может запустить загрузку скрипта.
- Известный пример опасного для такой проверки файла — `ce_new_attachable_item.script`: по информации владельца проекта, сканирование файлов с одним классом может вызвать критический сбой движка. Не считай чтение поля `_G` безопасной проверкой существования. Изучай такие исходники статически, не загружай их для анализа. Сохраняй базовые фильтры автозагрузчика (включая `ce_*`) и пользовательские исключения.

## Инициализация и автозагрузка

- Запуск после загрузки локации задаётся в `alife.ltx`: движок вызывает глобальную `ixr_on_start_game_callback()` из `ixray_system/global.lua` вместо `_G.start_game_callback`. Обёртка сначала вызывает оригинальную `_G.start_game_callback()`, затем, если доступен неймспейс, `ixr_framework.init()`. Сохраняй этот порядок и оригинальный вызов.
- Сам `ixr_framework.script` содержит входной метод `init`. Проверяй защиту от повторного входа и повторной инициализации; вызовы доступа к модулям также проходят через `init(false)`.
- В текущем пользовательском конфиге порядок такой: `ixr_signals`, `ixr_registry`, `ixr_options`, `ixr_storage`, `ixr_timers`, `ixr_triggers`, `ixr_throttlers`, затем `ixr_autoloader`.
- Автозагрузчик должен подключаться последним: он вызывает пользовательские `on_game_start`, которым уже нужны остальные модули. `ixr_options` заранее подписывается на окончание автозагрузки.
- Модуль возвращает из `get_module_info()` поля `alias_name`, `category`, `version`, `init_function_name`, `authors`, `description`. Имена alias и публичных функций являются контрактом. Поле `category` не заменяет явный порядок подключения в пользовательском конфиге.
- Внешний игровой код получает сервисы Framework только через глобальные методы `../ixray_system/global.lua`, глобальные методы событий `../ixray_system/dynamic_callbacks.lua` и данные/API, явно предоставляемые обратными вызовами. Прямые вызовы `ixr_framework.get_module`, `get_framework`, неймспейсов реализации, доступ через `_G` и чтение приватного состояния для обхода контракта не допускаются. Предпочитай готовую глобальную обёртку; если публичный контракт требует модуль, `GetModule`, `IsModuleLoaded`, `ClosureModuleIsExists` используют только alias (`"ixr_timers"`). Имена реализации используются при подключении модулей в предусмотренном `configure`, а не для доступа из обычного игрового кода.
- `ixr_autoloader` сканирует `.script`, применяет исключения, определяет наличие `on_game_start`, вызывает его с аргументом `"data"` и отправляет `on_ixr_autoloader_initialized`. Это инициализация, не покадровый поиск и регистрация подписок.
- Списки найденных скриптов кешируются в `level` named stash под ключами `ixr_framework_*`. Учитывай этот кеш при изменении поиска и исключений.
- Не полагайся на алфавитный порядок автозагрузки: `sort_script_files` сейчас распределяет записи из `pairs` по группам, а не сортирует имена.

## Стиль, производительность и проверка изменений

- Делай минимальные правки в соответствующей ответственности; сохраняй табы, `snake_case`, оформление соседнего кода, разделители секций и существующие публичные имена. Не форматируй целиком большой модуль ради одной функции.
- Перед добавлением парсера, проверки, клонирования, поиска, кеша, работы с файлами или векторами ищи готовое решение в `utils/` и прочитай его реализацию. Общие решения добавляй туда и переиспользуй через неймспейс.
- Сохраняй `nil` и `false` как разные значения. Проверяй места с `and/or`, значения по умолчанию, пустые массивы и словари; комментарии API сверяй с реализацией и фактическим вызывающим кодом.
- Горячие пути — `send_event`, actor/NPC/monster updates, таймеры, throttling и обновление UI. Не добавляй туда сканирование файлов, полный обход реестров, JSON/дисковый ввод-вывод, трассировку стека или подробный лог на каждый вызов без необходимости задачи.
- Инициализацию и регистрацию не переноси в update; сохраняй уже имеющиеся интервалы и кеши. Замер производительности не должен выполнять пользовательский callable ради оценки его сложности.
- При изменении API проверяй модуль, глобальную обёртку, пользовательский override и пример использования вместе. Изменения только инструкций не требуют запуска игры или сборки движка.
- Для функциональных изменений проверяй сценарии по затронутому контракту: повторная инициализация; подписка/отписка; новое и загруженное сохранение; несколько таймеров одновременно; вход/выход из триггера; программная и ручная смена опций. Не добавляй постоянные игровые тестовые скрипты без запроса пользователя.
