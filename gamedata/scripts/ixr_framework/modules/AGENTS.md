## Подключение и расширение

Для новой прикладной функциональности предпочитай отдельный модуль по обязательному шаблону, подключённый в нужном месте пользовательского списка. Изменять существующие модули Framework не рекомендуется: сначала проверь, не решается ли задача их публичным API, существующими событиями, новым модулем либо новым событием, зарегистрированным в публичном файле `../../__ixr_override_signals_intercepts.script`. Не достраивай чужую игровую ответственность внутри универсального модуля ради обхода его контракта. Изменение самого Framework требует архитектурного обоснования, если задача действительно относится к его развитию или исправлению.

Внешний доступ ограничен глобальными методами `../../ixray_system/global.lua`, методами событий `../../ixray_system/dynamic_callbacks.lua` и данными/API из предусмотренных обратных вызовов. Получение `_ref` в `on_init_ixr_options` — явный контракт; поиск внутренних таблиц или локалок модуля ради обхода этого контракта — нет. Системные обёртки и конфигурационные callbacks реализуют границу доступа, их внутренние вызовы не следует копировать в игровой код.

Игровые скрипты обращаются к модулю **только по alias_name** через глобальные `GetModule`, `IsModuleLoaded`, `ClosureModuleIsExists`, когда такой доступ нужен по публичному контракту. Прямое обращение внешнего игрового кода к `ixr_framework.get_module` запрещено; предпочитай готовую глобальную обёртку нужного сервиса. Пример: `GetModule("ixr_options")`. Имя `ixr_module_options` — имя реализации; доступ к нему из игрового кода через `GetModule("ixr_module_options")`, прямой неймспейс или `_G` категорически запрещён. Возможность менеджера найти модуль по имени скрипта не является разрешённым публичным контрактом для игровых скриптов. Подключение по имени реализации остаётся в `../../__ixr_override_framework_load_sub_modules.script`.

- Модуль предоставляет `get_module_info()` и указанную в `init_function_name` точку инициализации. Публичный API неймспейса обычно делегирует вызовы внутренней `local ixr_*` таблице; не открывай её как глобальную ради удобства вызова.
- Состав и порядок задаёт `../../__ixr_override_framework_load_sub_modules.script`, а не алфавит имён или `category`. Мододел может вставить собственный модуль в нужное место вызовом `load_module_by_script_name`.
- Соблюдай зависимости: сигналы должны быть готовы до подписок других модулей, опции — до завершения автозагрузки, автозагрузчик — последним. Не запускай модуль повторно из update.
- Проверяй глобальные обёртки в `../../ixray_system/global.lua` и `../../ixray_system/dynamic_callbacks.lua` вместе с изменяемым API. Caller-based идентификаторы зависят от глубины стека.
- Фильтр первичного разбора — `../../__ixr_override_autoload_system.script`. Он должен отсеивать проблемные и ненужные файлы до проверки `_G[script_name][function_name]`. Обращение может загрузить скрипт, а не просто проверить поле.
- Сохраняй исключения для опасных файлов. Известный пример от владельца проекта — `ce_new_attachable_item.script`; базовый фильтр `ce_*` уже есть в автозагрузчике. Не снимай фильтр для экспериментального сканирования и не загружай файл при анализе.
- Новые коллбеки регистрируй **только** в `../../__ixr_override_signals_intercepts.script`. Существующие default-регистрации в модуле не являются местом для добавления новых имён.

## Обязательный шаблон модуля

Управляемый модуль использует общий набор методов:

| Метод | Контракт |
| --- | --- |
| `get_module_info()` | Возвращает таблицу описания модуля с обязательными полями `alias_name`, `category`, `version`, `init_function_name`, `authors`, `description`. |
| `init()` | Выполняет инициализацию модуля; имя точки входа указано в `init_function_name`. Все текущие модули используют `"init"`. |
| `is_initialized()` | Возвращает состояние инициализации; входит в шаблон всех текущих модулей. |

Загрузчик проверяет доступность неймспейса скрипта, `get_module_info`, таблицу результата, наличие всех полей, уникальность alias и существование указанной функции инициализации. Затем сохраняет `script_name` и своё поле `initialized`, вызывает точку входа и отмечает модуль инициализированным. `is_initialized` входит в шаблон модуля, хотя отдельной проверки её наличия в загрузчике сейчас нет.

Методы прикладного API добавляются к этому набору и не заменяют его. `on_game_start` относится к автозагрузке обычных скриптов и не является заменой контракту управляемого модуля. Наличие внутренней `local ixr_*` таблицы само по себе также не регистрирует модуль.

## Уточнения архитектуры из документации

- Alias отделяет публичную идентичность модуля от имени файла реализации. Мододел может подключить обновлённую реализацию из другого файла с тем же alias без переписывания потребителей. Сохраняй публичный контракт и уникальность alias; одинаковый alias не означает разрешение зарегистрировать две реализации одновременно.
- Модули проектируются самодостаточными. Не связывай их с конкретными файлами реализации соседних модулей; для взаимодействия используй предусмотренные публичные контракты и события.
- В шаблоне `authors` допускает строку или массив авторов, `version` — числовую версию; `category` служит для информативности, а не автоматического вычисления зависимостей. Пример нового модуля содержит защиту от повторного `init`.
- Реестр в памяти предназначен в том числе для обмена ссылками на функции/объекты и флагами готовности между скриптами. Его не нужно сериализовать как Storage или использовать событие для каждого простого чтения общего значения. Флаги готовности не являются средствами синхронизации потоков C++.
- Storage имеет три публичные области: контекст вызывающего скрипта; контекст скрипта плюс ID объекта; общий shared-чанк. Одинаковые имена в разных изолированных областях не делают данные общими. В shared-области имена должны быть уникальны для её потребителей.
- Пространственные триггеры предназначены для онлайн-объектов и не заменяют проверку положения офлайн-сущностей ALife. Возврат true из callback означает запрос удаления триггера.
- Документированные пресеты опций используют возможность `option_return_value` быть функцией; обработчик вызывает её. Отличие ручного ввода от программного применения позволяет сбрасывать пресет на пользовательский без циклического переключения.
- Различай описание API и текущую реализацию: в документации Storage упомянут отдельный marshal-файл, а в текущем модуле используется `set_marshalized_data`/`get_marshalized_data`; сохранение триггеров, заявленное в документации, не следует выводить из имени модуля — при соответствующей задаче отдельно проследи путь регистрации и восстановления. Эти замечания не требуют сейчас менять код.

### Шина сигналов

Канонический шаблон добавления вызова или дополнительного кода аддона: в нужном месте общей функции отправить событие со **всеми необходимыми аргументами**, а реализацию разместить в отдельном обработчике аддона через `RegisterScriptCallback`. Передавай нужные объекты, значения, таблицы контекста и, если требуются, ссылки на функции-помощники; не заставляй аддон искать приватные данные или обращаться к внутренностям Framework. Общий исходник не должен напрямую зависеть от имени скрипта аддона, проверять наличие его конкретного метода или содержать его специфическую логику. При отсутствии подписчика дополнительный вызов просто не выполняется, и ванильная функция продолжает стандартную работу без ожидания ответа. Если требуется не дополнение, а замена ветки, явно предусмотри соответствующий слот функции/флаг и исходную ветку по умолчанию. Новое имя события регистрируется только в `__ixr_override_signals_intercepts.script`; каталог описывает порядок и назначение переданного контекста.

Канонический шаблон изменения значения через аддон: **до события** создать таблицу с исходным значением по умолчанию → передать её в событие → подписчик при необходимости меняет поле этой же таблицы → после отправки исходный код читает поле. Значение по умолчанию соответствует ванильному расчёту, а не произвольной заглушке. Если подписчика нет, таблица остаётся неизменной и используется ванильный результат. Пример существующего контракта: `local flags_table = {new_price = price}` перед событием изменения цены; после события — `price = flags_table.new_price`. Для такого механизма не передавай только отдельное число/строку/boolean в надежде изменить переменную вызывающего кода: изменяемым контейнером служит таблица.

Главное условие интеграционных событий: отсутствие или удаление аддона не меняет и не блокирует ванильное поведение. Подписчик не обязан существовать. Начальные значения контекста и ветка без функтора сохраняют исходную логику; ожидание ответного события или состояния, которое может установить только аддон, недопустимо для продолжения ванильной операции.

Шина поддерживает обвязки над ванильной логикой, а не только уведомления. Паттерны: изменить значение в общей таблице, запретить ветку через предусмотренный флаг, установить функтор вместо стандартной реализации или выполнить дополнительный код в нужном месте. Исходная функция продолжает выполнение после синхронной отправки и читает результат из контекста. Примеры: цена в `inventory_upgrades`, функторы в `death_manager`, позиция NPC в `xr_motivator`, флаг `allow` в `surge_manager`. Полный пример — [карта игровых скриптов](../../AGENTS.md).

Шина игнорирует результаты `return` обычных подписчиков. Функция, записанная в поле контекста, вызывается исходным кодом отдельно; её контракт и возвращаемое значение определяет эта точка вызова. Не смешивай эти два этапа и движковую замену методов.

- Сохраняй контракт `RegisterScriptCallback(name, function_or_object)`, `UnregisterScriptCallback(name, function_or_object)` и `SendScriptCallback(name, ...)`, включая алиасы `callback_set`, `callback_unset`, `make_callback`.
- Сейчас подписки хранятся как `intercepts[event][function_or_object] = true`. Это не массив структур: повторная подписка той же ссылки заменяет тот же ключ, отписка удаляет его. Не меняй это представление без задачи на изменение контракта.
- Функция получает `...`; для объекта вызывается `object[event](object, ...)`. Порядок и состав аргументов менять нельзя.
- `send_event` обходит подписчиков через `pairs`: порядок подписки не гарантирован. Плоские массивы в других частях фреймворка имеют собственный порядок, не превращай их в словари.
- Каталог новых событий расширяется только в `../../__ixr_override_signals_intercepts.script`.
- Событие должно существовать до подписки: для неизвестного имени текущий код подписку не создаёт. `args_map` — прежде всего публичная подсказка мододелу в каталоге событий: из неё переносят аргументы в обработчик в том же порядке. Строки описывают имя/роль/применение и не обязаны совпадать с реальными игровыми типами. Они также попадают в лог регистрации, но не валидируют, не преобразуют и не связывают аргументы по именам при отправке. Реальные значения задаёт `SendScriptCallback`; для неоднозначного обозначения сверяй место отправки.
- При пользовательском `__ixr_override_signals_intercepts` модуль добавляет базовые addon-intercepts и вызывает `configure`; полный default-каталог при этом не применяется.
- Отправка синхронная. Общие таблицы аргументов (`flags`, описание предмета и т. п.) передавай теми же ссылками, чтобы изменения подписчиков оставались видны вызывающему коду.
- Движковая подмена функций уже обновляет сохранённые ссылки. Не добавляй разрешение подмен на каждый `send_event`, повторную подписку или Lua-пересборку шины ради работы инжектора.

### Хранилище, таймеры и throttling

**Назначение сервисов:** модуль таймеров ориентирован прежде всего на сюжетные моменты и отложенные игровые действия, которым необходимо сохраняемое состояние. По пояснению владельца проекта, механизм сохранения здесь недешёвый: не используй Timer API как обычную техническую отсечку для частых обновлений и вспомогательных операций внутри скриптов. Если функция уже вызывается на update, сначала рассматривай `IsActionThrottled`.

Модуль триггеров аналогично предназначен для геймплея: сюжетных/игровых зон, реакций на вход, нахождение и выход объектов. Не используй его как универсальную служебную инфраструктуру для внутренних проверок скрипта, не связанных с игровой пространственной механикой. Само наличие готового модуля не означает, что его нужно подключать к любой похожей по названию задаче. Конкретный путь сохранения и его стоимость у таймеров и триггеров не считай одинаковыми без проверки реализации.

- Глобальные Storage-обёртки определяют скрипт-владельца через `ffx_callable_utils.find_caller_source(3)`. Есть отдельные варианты для объекта и общей ячейки `shared_chunk`. Новые уровни обёрток могут изменить владельца данных.
- `init` хранилища и фактическая загрузка данных — разные состояния. `get_var`/`set_var` требуют загруженное хранилище; сохраняй проверки режима редактора и загрузки.
- Активный путь сохранения использует `marshal.encode/decode` и `set_marshalized_data`/`get_marshalized_data`. Комментарии про отдельный `.ixr` файл не означают, что сейчас ведётся такая запись.
- Не меняй без необходимости структуру `m_storage = {mod_version, chunks}` и записи `{var_type, var_value}`. Для преобразований типов проверь обе стороны `casts` и сценарий save/load.
- Таймеры ждут появления актора и `on_load_screen_await_any_key_pressed`; загрузка их состояния происходит на первом подходящем actor update. Шаг обработки — минимум 50 мс, время измеряется в миллисекундах `time_global()`.
- `timer_create(name, loop, auto_paly, left_milliseconds, callable_fn, ...)` возвращает объект с `name`, `exists`, `play`, `stop`, `delete`. Сохраняй позиционные аргументы и существующие публичные имена, включая `auto_paly`.
- Таймеры лежат в плоском массиве. Их `serialized_callable` — структура `{fn, args}`, не строковый код. При изменении удаления учитывай сдвиг индексов и несколько истёкших таймеров за один проход.
- `is_action_throttled` использует время, кешируемое на `actor_on_update`; `false` разрешает действие, `true` запрещает. Интервал запоминается при первом обращении к имени. Не вводи общий ключ для независимых действий разных скриптов.
- Триггеры хранятся по уровню и имени, отслеживают ID внутри зоны. Обработчик получает `(level, name, center, radius, object, position, entered, inside, exited, source)`, а истинный результат запрашивает удаление триггера.
- Ограничители проверки триггеров сейчас общие для actor/NPC/monster по отдельности, не индивидуальны для каждого объекта. Не предполагай, что каждый NPC проверяется раз в 100 мс.

### Практический выбор: throttling вместо таймера на update

`IsActionThrottled` можно использовать как лёгкую временную отсечку, если функция уже вызывается из update, но её работу требуется выполнять реже. Это типовой пример применения готового API по смыслу задачи, а не только по названию функции.

```lua
function on_game_start()
	RegisterScriptCallback("actor_on_update", function()
		if IsActionThrottled("my_feature.periodic_scan", 500) then
			return
		end

		-- Нужная работа: не чаще одного раза за 500 мс при поступающих update.
	end)
end
```

Проверка остаётся на каждом update, а код после неё выполняется реже. Это не запланированный вызов: без новых update отсечка ничего не запускает, пропущенные интервалы не воспроизводятся. Timer API выбирай для сюжетного/игрового отложенного действия, когда действительно требуются сохраняемое состояние, пауза/продолжение и соответствующий жизненный цикл. Не считай его стандартным выбором для любой технической задержки внутри скрипта.

Имя отсечки должно быть постоянным и уникальным для задачи, чтобы независимые операции не блокировали друг друга. Не создавай новое имя на каждом кадре. `true` означает пропустить работу, `false` — выполнить; не инвертируй условие. Для такой задачи не создавай отдельный таймер, модуль или собственную таблицу времён, если существующей отсечки достаточно. Особенности кешируемого времени и интервала, запоминаемого при первом обращении, описаны выше.

### Опции

- Образец для пользовательских опций — `../example_options/ixr_options_template.script`. Настройки команды добавляй в `ixray_options/ixray_global_options.script`; универсальные контроллы и поведение — в модуль опций.
- В `on_game_start` задаются метаданные страницы через `SetOptionTitle`, `SetOptionAddonName`, `SetOptionScriptVersion`, `SetOptionAuthors`, `SetOptionIcon` и регистрируется подписка на `on_init_ixr_options`.
- На `on_init_ixr_options` приходит явно предоставленная контрактом таблица API `_ref`. Обработчик устанавливается замыканием в `on_game_start`, а вызывается фреймворком при регистрации опций. Вложенные обработчики могут захватывать `_ref` для предусмотренных операций; наличие глобальных функций не делает такой доступ нелегитимным и не требует его переписывать. Регистрация: `_ref.register_option(group, name, display_text, controll_data, callback)`. `group = nil` означает опцию без группы.
- Готовые фабрики: `check_box`, `text_box`, `combo_box`, `combo_box_item`, `numeric_up_down`, `track_bar`, `ceil_track_bar`. Используй их, не копируй реализацию UI-классов в вызывающие скрипты.
- Контракт обработчика: `(group, name, value, is_value_from_code)`. Сохраняй различие программного изменения и ручного ввода: оно нужно пресетам для защиты от циклических переключений.
- Комбобокс хранит индекс, но обработчик и `GetOptionsVar` получают `option_return_value`. Оно может быть таблицей или функцией; не подменяй его индексом. `SetOptionsVar` для комбобокса задаёт индекс.
- Ключ хранилища опций строится как `script_name .. "_" .. var_name`. Определение вызывающего скрипта и глубина стека влияют на область опций; не меняй их случайно при добавлении обёрток.
- Файл пользовательских настроек — JSON `ixr_options.ixr` в `$app_data_root$`, отдельно от данных сейва. Сохраняй формат `{value, metadata}`, механизмы видимости и обновления UI.
- В `ixr_options` есть update bus с интервалом 100 мс, обновление визуального значения и навигация геймпадом. При правке контролла проверь и мышь/клавиатуру, и геймпад, и программное изменение.

## Проверка изменений модулей

- Выбирай проверки по затронутой ответственности: повторный init; подписка и отписка; сохранение/загрузка; несколько одновременно завершившихся таймеров; смена уровня и граница триггера; опции до построения меню и после него.
- При правке таймеров проверь очередь удаления и локальное накопление индексов: сдвиг массива не должен пропустить следующий таймер. Не меняй форматы сохранения одновременно с несвязанной правкой.
- Ошибки `false`/`nil`, порядок массивов и реальная глубина caller lookup проверяются по реализации, а не только по комментариям. Исправления существующих дефектов не включай молча в постороннюю задачу.
- Подробности производных событий: [extend_callbacks](../extend_callbacks/AGENTS.md); публичных помощников: [public_components](../public_components/AGENTS.md); общих решений: [utils](../utils/AGENTS.md).
