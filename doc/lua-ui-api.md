# Lua UI: окна, статики и события мыши

Документация по изменениям от 7 ноября 2026 года. Описывает API в исходниках;
для его использования нужно пересобрать соответствующие модули движка.

## Что добавлено

| API | Назначение | Модуль |
| --- | --- | --- |
| `CreateScriptWindow()` | Создание скриптового окна без объявления Lua-класса | `xrGame` |
| `control:AddSelfCallback(event, handler)` | Подписка на событие самого контрола без имени и `Register` | `xrUI` |
| `window:AddCallback(name, event, function)` | Обработчик события без обязательного объекта `self` | `xrGame` |
| `xml:InitNoXmlStatic(name, x, y, width, height, parent)` | Создание и прикрепление статика без чтения XML | `xrGame` |
| `GetCurrentDialogHolder()` | Получение текущего держателя UI без открытия вспомогательного диалога | `xrUI` |
| `GetMainMenuWindow()` | Ссылка на уже созданное корневое окно главного меню как `CUIScriptWnd`, без правки его Lua-скрипта | `xrGame` |
| `IsMainMenuActive()` | Проверка активности главного меню | `xrGame` |
| `control:ToFront()`, `control:ToBack()` | Изменение порядка отрисовки среди детей текущего родителя | `xrUI` |
| `ui_events.MOUSE_*` | Восемь событий мыши для зарегистрированных статиков | `xrUI`, `xrGame` |
| `ui_events.WINDOW_FOCUS_RECEIVED`, `ui_events.WINDOW_FOCUS_LOST` | Экспорт существующих событий входа и выхода курсора | `xrUI` |
| `static:SetFontByName(name)` | Выбор шрифта по имени секции, как в XML `font` | `xrUI` |
| `static:HighlightText(enabled)`, `static:SetHighlightColor(color)` | Включение и цвет подсветки текста при наведении | `xrUI` |
| `TextureOn()`, `TextureOff()`, `TextOn()`, `TextOff()` | Раздельное включение текстуры и текста | `xrUI` |

`CUIStatic()`, `SetWndPos`, `SetWndSize`, `SetFont`, `SetText`,
`SetTextColor`, `SetTextureColor`, `SetStretchTexture`, `AttachChild`,
`AddDialogToRender` и `RemoveDialogToRender` уже существовали.

## 1. Самостоятельная отрисовка текста

Полный пример для запуска в главном меню или при доступном игровом HUD.
Не требует переменных от предыдущих запусков:

```lua
function remove_control()
    if ui_state then
        ui_state.holder:RemoveDialogToRender(ui_state.control)
        ui_state = nil
    end
end

remove_control()

local holder = GetCurrentDialogHolder()
assert(holder, "No active UI holder")

local control = CUIStatic()
control:SetWndPos(vector2():set(0, 0))
control:SetWndSize(vector2():set(300, 60))
control:SetFont(GetFontLetterica16Russian())
control:SetText("Text")
control:SetTextColor(GetARGB(255, 255, 255, 255))

ui_state = { holder = holder, control = control }
holder:AddDialogToRender(control)
log1("Control added")
```

Убрать текст в той же UI-сессии:

```lua
remove_control()
```

Это пример только отрисовки: ввод остаётся у меню или игры. Открывать временный
`CUIDialogWnd` и получать через него holder не нужно. Сам по себе статик не рисует
фон окна: без текстуры виден только заданный текст. Консоль и окна отладчика могут
перекрывать текст в верхнем левом углу; для проверки их нужно закрыть или свернуть.

`GetCurrentDialogHolder()` возвращает доступный holder активного главного меню.
Если активного holder меню нет, возвращает holder доступного игрового HUD,
даже когда в нём не открыто ни одного диалога. Если UI ещё недоступен, возвращает `nil`.
Функция не создаёт окно, не захватывает ввод и не перемещает курсор.

Инвентарь и другие игровые диалоги — окна внутри holder HUD, а не отдельные
holder. Текущее окно ввода возвращается через `holder:TopInputReceiver()`;
при отсутствии такого окна результат `TopInputReceiver()` равен `nil`,
но сам holder HUD остаётся доступным.

### Ссылка на окно главного меню

| Функция | Возвращаемое значение |
| --- | --- |
| `GetMainMenuWindow()` | Существующий `CUIScriptWnd` главного меню или `nil`, если подходящего окна нет |
| `IsMainMenuActive()` | `true`, когда главное меню активно; иначе `false` |

```lua
local window = GetMainMenuWindow()
local active = IsMainMenuActive()

if window and active then
    local xml = CScriptXmlInit()
    local control = xml:InitNoXmlStatic("control", 10, 20, 200, 30, window)
    control:SetText("Text")
    control:AddSelfCallback(ui_events.MOUSE_LEFT_CLICK, function(control)
        control:SetText("Updated text")
    end)
end
```

Изменять Lua-скрипт меню, сохранять `self` в глобальную переменную или создавать
вспомогательное окно не требуется. `GetMainMenuWindow()` возвращает существующее
корневое окно меню как `CUIScriptWnd`, с методами `Register`, `AddCallback`,
`GetStatic` и другими методами скриптового окна. Это не объект управления
`CMainMenu` и не текущий верхний модальный диалог. Функция не активирует меню
и не вызывает загрузку его UI.

Если UI меню ещё не создан, уже уничтожен или корень меню не является
`CUIScriptWnd` в текущей конфигурации, возвращается `nil`. Созданное
окно может существовать при закрытом меню, поэтому для проверки открытого меню
используется отдельный `IsMainMenuActive()`. Он возвращает `false`, если объект
меню недоступен, и отражает штатный флаг активности меню движка.

Возвращённое окно принадлежит движку: не удаляйте его и не меняйте его владение.
Меню может пересоздать UI, например при смене разрешения. Не используйте прежнюю
ссылку после пересоздания; повторно получите её через `GetMainMenuWindow()`.
Ссылки на прикреплённые к старому меню контролы также не переживают его удаление.

## 2. Окно без Lua-класса

Для создания окна без объявления Lua-класса используется фабрика:

`CreateScriptWindow()` только создаёт объект. Окно не добавляется в отрисовку
автоматически. Для отрисовки нужен `holder:AddDialogToRender(window)`,
для интерактивного диалога — `window:ShowDialog(false)`.

```lua
local holder = GetCurrentDialogHolder()
assert(holder, "No active UI holder")

window = CreateScriptWindow()
window:SetWndPos(vector2():set(0, 0))
window:SetWndSize(vector2():set(300, 40))
window:SetStopAnyMove(false)

local xml = CScriptXmlInit()
local control = xml:InitNoXmlStatic(
    "control", 0, 0, 300, 40, window
)
control:SetFont(GetFontLetterica16Russian())
control:SetTextColor(GetARGB(255, 255, 255, 255))
control:SetText("Text")

window:Register(control, "control")
holder:AddDialogToRender(window)
```

При работе непосредственно с игровым HUD вместо `holder` можно использовать
результат `get_hud()`, если HUD доступен.

Обновление из игровой логики:

```lua
window:GetStatic("control"):SetText("Updated text")
```

`CreateScriptWindow()` возвращает объект `CUIScriptWnd`, созданный как обычный
C++ `CUIDialogWndEx`, без обёртки виртуальных вызовов в Lua. Он поддерживает
дочерние контролы, `Register`, `GetStatic` и `AddCallback`.

Виртуальные `Update`, `OnKeyboard`, `Dispatch` и другие обработчики используют
реализацию C++. Если нужно переопределять их в Lua, используется прежнее
наследование от `CUIScriptWnd`. Фабрика не заменяет этот механизм.

## 3. Создание статика через CScriptXmlInit без XML

Сигнатура:

```lua
local control = xml:InitNoXmlStatic(name, x, y, width, height, parent)
```

| Аргумент | Значение |
| --- | --- |
| `name` | Имя контрола; может использоваться в `Register`, `GetStatic` и коллбеках |
| `x`, `y` | Позиция относительно родителя |
| `width`, `height` | Размер в координатах UI |
| `parent` | Родительский `CUIWindow`; обязателен |

Метод вызывается у экземпляра `CScriptXmlInit`:

```lua
local xml = CScriptXmlInit()
local control = xml:InitNoXmlStatic("control", 0, 0, 200, 30, window)
```

Для этого вызова `ParseFile()` не требуется. Метод не читает XML и не требует
узла-заглушки. Остальные методы того же `CScriptXmlInit` могут продолжать работать
с XML, загруженным через `ParseFile`.

Созданный статик получает имя, позицию, размер и системный шрифт; прикрепляется
к родителю с автоматическим удалением. Изначально он показан и включён, но не
содержит текста или текстуры. Для `CUIScrollView` используется `AddWindow`.
При `parent == nil` возвращается `nil`.

`InitNoXmlStatic` не вызывает `Register`. Для прежней подписки по имени контрол
регистрируется отдельно у нужного `CUIScriptWnd`:

```lua
window:Register(control, "control")
```

Это требуется только для прежней подписки по имени через `AddCallback`.
Прямая подписка на возвращённый статик работает без `Register`:

```lua
local control = xml:InitNoXmlStatic("control", 10, 20, 200, 30, window)
control:AddSelfCallback(event, handler)
```

`event` — значение из `ui_events`, `handler` — функция, принимающая
контрол-источник. Например, `ui_events.MOUSE_LEFT_CLICK` и
`function(control) ... end`. Имя, заданное при создании, для этой подписки
не используется.

Повторно прикреплять этот контрол через `AttachChild` не нужно.

### Изображение

```lua
local control = xml:InitNoXmlStatic("image", 10, 20, 128, 64, window)
control:InitTexture(texture_name)
control:SetStretchTexture(true)
control:SetTextureColor(GetARGB(200, 255, 255, 255))
```

`texture_name` — существующая в текущей сборке текстура или имя из атласа.
Создание без XML не создаёт сам ресурс. Имена ресурсов задаются через `texture_name`; они не берутся из XML.
При записи пути строкой Lua учитывайте экранирование обратного слеша.

### Текст и шрифт по имени

```lua
local control = xml:InitNoXmlStatic("control", 10, 20, 200, 30, window)
control:TextureOff()
control:SetFontByName(font_name)
control:SetTextAlignment(0)
control:SetVTextAlignment(0)
control:SetTextComplexMode(true)
control:SetText("Text")
control:SetTextColor(GetARGB(150, 255, 255, 255))
control:HighlightText(true)
control:SetHighlightColor(GetARGB(150, 255, 0, 0))
```

Секция с именем из `font_name` должна существовать в конфигурации шрифтов игры.
`SetFontByName` использует тот же менеджер, что XML-атрибут `font`.
Прежний `SetFont(font_object)` сохранён.

`GetFontLetterica16Russian()` возвращает объект `CGameFont`, а не имя секции.
Поэтому его результат передаётся в `SetFont`. Для имени секции из `fonts.ltx`
используется строка `font_name` и метод `SetFontByName(font_name)`.

Горизонтальное выравнивание: `0` — влево, `1` — вправо, `2` — по центру,
`3` — по ширине. Вертикальное: `0` — сверху, `1` — по центру, `2` — снизу.
`GetARGB(a, r, g, b)` принимает альфа-канал первым.

`HighlightText(true)` включает цвет при наведении; `SetHighlightColor` задаёт
этот цвет. Основной цвет задаётся через `SetTextColor`. Для обычного `CUIStatic`
узлы `<text_color><e/>...<h/></text_color>` не читаются методом `InitStatic`:
состояния этих узлов настраиваются отдельно для кнопок. В примере выше подсветка
статика включена явно.

### Прямой CUIStatic()

Конструктор уже существовал. При ручном прикреплении нужно передать владение
родителю:

```lua
local control = CUIStatic()
control:SetWndPos(vector2():set(0, 0))
control:SetWndSize(vector2():set(200, 30))
control:SetFont(GetFontLetterica16Russian())
control:SetText("Text")
control:SetTextColor(GetARGB(255, 255, 255, 255))
control:SetAutoDelete(true)
window:AttachChild(control)
window:Register(control, "control")
```

Добавлены проверки отсутствующего шрифта в `SetTextAlign` и `AdjustWidthToText`,
а также начальные значения цвета подсветки и флага наличия XML-текста.
Эти изменения не подтверждают причину любого прежнего вылета пустого конструктора.

## 4. События мыши

Контрол должен участвовать в обработке ввода и обновлении UI. Для подписки
непосредственно на нём используйте `control:AddSelfCallback(event, handler)`:
имя и `Register` не нужны. Для прежней подписки по имени контрол регистрируется
у `CUIScriptWnd`, затем вызывается `window:AddCallback(name, event, handler)`.
`Register` задаёт получателя сообщений и включает уведомления мыши для статика.

| Событие | Когда вызывается |
| --- | --- |
| `ui_events.MOUSE_LEFT_CLICK` | Нажатие ЛКМ внутри контрола; второе нажатие двойного клика тоже учитывается |
| `ui_events.MOUSE_RIGHT_CLICK` | Нажатие ПКМ внутри контрола |
| `ui_events.MOUSE_ENTER` | Курсор вошёл в прямоугольник контрола |
| `ui_events.MOUSE_LEAVE` | Курсор покинул прямоугольник после входа |
| `ui_events.MOUSE_DRAG` | Движение внутри контрола с зажатой ЛКМ или ПКМ |
| `ui_events.MOUSE_MOVE` | Движение внутри контрола, в том числе при зажатой кнопке |
| `ui_events.MOUSE_WHEEL_UP` | Прокрутка колеса вверх внутри контрола |
| `ui_events.MOUSE_WHEEL_DOWN` | Прокрутка колеса вниз внутри контрола |
| `ui_events.WINDOW_FOCUS_RECEIVED` | Экспорт существующего события входа курсора; то же значение, что `MOUSE_ENTER` |
| `ui_events.WINDOW_FOCUS_LOST` | Экспорт существующего события выхода курсора; то же значение, что `MOUSE_LEAVE` |
| `ui_events.WINDOW_UPDATE` | Вызов подписанного обработчика при существующем обновлении окна или контрола |

Перечислено одиннадцать основных имён: восемь `MOUSE_*`, два `WINDOW_FOCUS_*`
и `WINDOW_UPDATE`. Enter/leave используют существующие события движка;
остальные шесть уведомлений мыши отправляются новой обработкой статика.
Первоначальные восемь имён `on_mouse_*` сохранены как совместимые алиасы
одноимённых `MOUSE_*`; в новых скриптах используются имена в верхнем регистре.

Для уведомлений мыши используйте `MOUSE_*`. Прежний `WINDOW_MOUSE_MOVE`
остаётся обозначением входного действия и не является алиасом нового
`MOUSE_MOVE`.

`MOUSE_ENTER` и `MOUSE_LEAVE` — алиасы существующих событий
`WINDOW_FOCUS_RECEIVED` и `WINDOW_FOCUS_LOST`, которые также экспортированы.
Это фокус наведения мыши, а не клавиатурный фокус. Проверка происходит при
обновлении UI, пока курсор виден, и не учитывает перекрытие другим контролом.
Скрытие окна само по себе не означает `MOUSE_LEAVE`.

При перетаскивании приходят и `MOUSE_MOVE`, и `MOUSE_DRAG`. Нажатие может
начаться вне контрола. Захват мыши, перемещение контрола и определение расстояния
перетаскивания автоматически не выполняются.

Клик здесь означает нажатие, а не пару «нажать и отпустить», как у обычной кнопки.
События не поглощают ввод: перекрывающиеся статики могут получить одно событие.
Если дочерний контрол поглотил событие, родительский статик его не получит.

### Коллбек без класса

```lua
window:Register(control, "control")
window:AddCallback("control", ui_events.MOUSE_LEFT_CLICK, function()
    local position = GetCursorPosition()
    log1("Clicked at " .. tostring(position.x) .. ", " .. tostring(position.y))
end)
```

Эта подписка работает по имени контрола через окно. Трёхаргументная форма
`AddCallback` вызывает функцию без аргументов. Для подписки непосредственно
по ссылке на контрол используется отдельный метод `AddSelfCallback`, описанный ниже.
Прежняя форма с объектом сохранена:

```lua
window:AddCallback("control", ui_events.MOUSE_LEFT_CLICK, handler, object)
```

Она вызывает `handler(object)`. Координаты, кнопка и величина колеса в аргументы
коллбека не передаются. `GetCursorPosition()` возвращает координаты UI на экране;
они не переводятся автоматически в локальные координаты контрола.
Используйте уникальные имена контролов: существующий диспетчер вызывает первый
совпавший обработчик, а не все коллбеки с одинаковой парой «имя, событие».

### Анонимная подписка через ссылку на контрол

```lua
control:AddSelfCallback(ui_events.MOUSE_LEFT_CLICK, function(control)
    control:SetText("Updated text")
end)
```

Сигнатура: `control:AddSelfCallback(event, handler)`. Имя контрола и вызов
`window:Register` не нужны. Подписка хранится в самом контроле; при его
уничтожении обработчики освобождаются автоматически. Отдельный `Unregister`
для такой подписки не требуется.

Обработчик получает ссылку на контрол-источник. Если аргумент не нужен,
допустимо объявить `function() ... end`. Для работы с источником используйте
переданный аргумент, а не захватывайте тот же контрол в замыкании: так обработчик
не удерживает дополнительную Lua-ссылку на самого себя.

На одно событие можно добавить несколько обработчиков: все вызываются в порядке
подписки. Добавленный во время вызова обработчик начнёт участвовать со следующего
события. Возвращаемое значение обработчика игнорируется и не поглощает ввод.
`pData` и другие дополнительные данные C++-сообщения в обработчик не передаются.

Сначала вызываются собственные подписки контрола, затем сохраняется обычная
отправка сообщения его получателю, включая прежние коллбеки по имени.
При отсутствии `AddSelfCallback` используется прежняя маршрутизация.

Подписка не добавляет контрол в отрисовку и не делает его получателем ввода.
Для кликов окно должно участвовать в обработке ввода. Наведение проверяется
отдельно при обновлении и видимом курсоре.

При `keep_lua`, скрытии или снятии живого контрола с очереди обработчики остаются
частью этого объекта. Они освобождаются при уничтожении контрола, а не при
каждом `Show(false)` или `RemoveDialogToRender`.

#### Полный пример без имён контролов

```lua
window = CreateScriptWindow()
window:SetWndPos(vector2():set(0, 0))
window:SetWndSize(vector2():set(400, 100))

local control = CUIStatic()
control:SetWndPos(vector2():set(0, 0))
control:SetWndSize(vector2():set(300, 60))
control:SetFont(GetFontLetterica16Russian())
control:SetText("Text")
control:SetTextColor(GetARGB(255, 255, 255, 255))
control:SetAutoDelete(true)
window:AttachChild(control)

control:AddSelfCallback(ui_events.MOUSE_LEFT_CLICK, function(control)
    control:SetText("Updated text")
end)

window:Show(false)
window:ShowDialog(false)
```

Окно открывается как интерактивный диалог. Для закрытия вызовите
`window:HideDialog()`, затем освободите ссылку на окно. Это не удаление подписки:
обработчики дочернего контрола освободятся при его удалении вместе с родителем.

#### Классы, которым доступен AddSelfCallback

Метод экспортирован у `CUIWindow` и наследуется через Lua-цепочку базовых классов.
Ниже приведены именно имена классов в Lua. Наличие конструктора у каждого
класса не подразумевается: метод также доступен на контролах, возвращённых движком.
Для классов, отсутствующих в текущей конфигурации сборки, таблица не создаёт
дополнительного экспорта.

| Группа | Имена классов в Lua |
| --- | --- |
| Базовые окна и диалоги | `CUIWindow`, `CUIDialogWnd`, `CUIScriptWnd` |
| Статики и оформление | `CUIStatic`, `CUIArrow`, `CUIFrameWindow`, `CUIFrameLineWnd`, `CUIStackPanel`, `CUIGamepadLegend`, `UIHint` |
| Кнопки | `CUIButton`, `CUI3tButton`, `CUICheckButton`, `CUITabButton` |
| Пошаговый выбор значения | `CUICustomSpin`, `CUISpinNum`, `CUISpinFlt`, `CUISpinText` |
| Поля ввода | `CUICustomEdit`, `CUIEditBox` |
| Списки и элементы | `CUIScrollView`, `CUIListBox`, `CUIListBoxItem`, `CUIListBoxItemMsgChain`, `CUIListWnd`, `CUIListItem`, `CUIListItemEx` |
| Управление значениями и вкладками | `CUITrackBar`, `CUIArrowStepper`, `CUIScrollBar`, `CUITabControl`, `CUIComboBox`, `CUIPropertiesBox`, `CUIProgressBar` |
| Сообщения | `CUIMessageBox`, `CUIMessageBoxEx` |
| Игровые окна | `CUIActorMenu`, `CUIPdaWnd`, `CUIMainIngameWnd`, `CUIMotionIcon`, `CUIHudStatesWnd` |
| Дополнительные окна | `CServerList`, `CUIMapList`, `CUIMMShniaga` |

Всего в таблице 44 Lua-класса. Объект, возвращённый `CreateScriptWindow()`,
использует API `CUIScriptWnd` и также поддерживает `AddSelfCallback`.

`CDialogHolder`, `CUIGameCustom`, `CMainMenu`, `CUILines`, `CGameFont`,
`CUIZoneMap` и `CUICompassBar` не получают этот метод: в их Lua-экспортах нет
нужной цепочки наследования от `CUIWindow`.

#### Какие события приходят конкретному классу

Наличие `AddSelfCallback` не означает генерацию любого события из `ui_events`.
Метод обрабатывает собственные уведомления контрола; события дочерних элементов
автоматически не превращаются в события родителя.

| Класс или семейство | Примеры собственных событий |
| --- | --- |
| `CUIWindow` и производные, вызывающие базовый `Update` | `WINDOW_UPDATE` — только при явной подписке |
| `CUIStatic` | Все восемь `MOUSE_*`; подписка сама включает отправку уведомлений мыши |
| `CUIButton`, `CUI3tButton` | `BUTTON_DOWN`, `BUTTON_CLICKED` |
| `CUICheckButton` | `BUTTON_CLICKED`; обработка мыши у этого класса отличается от обычного статика |
| `CUICustomSpin` и производные | `BUTTON_CLICKED` при изменении значения |
| `CUITabControl`, `CUITabButton` | `TAB_CHANGED` |
| `CUITrackBar`, `CUIArrowStepper` | `TRACK_VALUE_CHANGED` |
| `CUIScrollBar` | `SCROLLBAR_HSCROLL`, `SCROLLBAR_VSCROLL` |
| `CUIListBox`, `CUIListWnd`, элементы списков | Собственные `LIST_ITEM_*`, которые отправляет конкретный класс |
| `CUIComboBox` | `LIST_ITEM_SELECT` |
| `CUIPropertiesBox` | `PROPERTY_CLICKED` |
| `CUICustomEdit`, `CUIEditBox` | `EDIT_TEXT_COMMIT`; доступность остальных событий зависит от текущего экспорта `ui_events` |
| `CUIMessageBox`, `CUIMessageBoxEx` | Собственные `MESSAGE_BOX_*` |

Базовые enter/leave используют `WINDOW_FOCUS_RECEIVED` и `WINDOW_FOCUS_LOST`,
то есть алиасы `MOUSE_ENTER` и `MOUSE_LEAVE`. Их наличие также зависит от того,
вызывает ли конкретный класс базовую обработку наведения. Производный контрол
может переопределять обработку мыши; не следует считать восемь событий статика
универсальными для каждого класса из таблицы.

### Подписка на обновление без класса

```lua
window = CreateScriptWindow()
window:SetWndPos(vector2():set(0, 0))
window:SetWndSize(vector2():set(300, 60))

window:AddSelfCallback(ui_events.WINDOW_UPDATE, function(window)
    local control = window:GetStatic("control")
    if control then
        control:SetText("Text")
    end
end)

local holder = GetCurrentDialogHolder()
assert(holder, "No active UI holder")
holder:AddDialogToRender(window)
```

`WINDOW_UPDATE` не создаёт таймер, не добавляет окно в scheduler и не вызывает
`Update` принудительно. Обработчик вызывается только при существующем обновлении
окна через holder или родительский контрол, после обновления дочерних элементов
в базовом `CUIWindow::Update`. Без подписки на `WINDOW_UPDATE` соответствующего
вызова Lua нет; подписка только на мышь не включает обработчик обновления.

`WINDOW_UPDATE` — собственное уведомление для `AddSelfCallback`. Оно не отправляется
родителю и не обслуживается старым `AddCallback(name, event, handler)`.
Аргумент функции — обновляемое окно. Отдельные параметры времени не передаются.
Частоту определяет существующая обработка UI, а не подписка.

Если Lua-класс переопределил `Update` и не вызывает базовый метод, базовая
подписка на обновление не выполняется. Само переопределение `Update` и порядок
вызовов прежних классов не изменены.

## 5. Отрисовка и интерактивный диалог

| Вызов | Результат |
| --- | --- |
| `window:Show(true)` | Меняет видимость; сам по себе не добавляет окно в отрисовку |
| `holder:AddDialogToRender(window)` | Добавляет отрисовку и обновление; не захватывает ввод |
| `holder:RemoveDialogToRender(window)` | Снимает с очередей отрисовки; скрывает и отключает окно, если нашлась регистрация |
| `window:ShowDialog(false)` | Открывает диалог через текущий holder и делает его получателем ввода |
| `window:HideDialog()` | Закрывает интерактивный диалог и возвращает ввод предыдущему получателю |

Для интерактивного окна вместо `AddDialogToRender` используется:

```lua
window:Show(false)
window:ShowDialog(false)
```

`false` здесь означает «не скрывать игровые индикаторы», а не «не перехватывать
ввод». Обычный диалог по умолчанию центрирует курсор и может блокировать управление
игрой. Для окна без захвата ввода используется только `AddDialogToRender`.
`SetStopAnyMove(false)` управляет остановкой движения персонажа, но не превращает
открытый диалог в прозрачный для кликов оверлей.

Клики и колесо требуют маршрутизации ввода в окно. Окно, добавленное только через
`AddDialogToRender`, не становится получателем этих событий. Проверка наведения
отдельна: обновляемый контрол может получать enter/leave при видимом курсоре.

### Проверка наведения

```lua
local hovered = control:IsCursorOverWindow()
local preciseHovered = control:IsCursorOverWindow(true)
```

Вызов без аргумента или с `false` сохраняет прежнее поведение: возвращает
состояние попадания курсора в прямоугольник, рассчитанное при `Update()`.

Аргумент `true` проверяет текущую позицию видимого курсора с учётом видимости
и доступности контролов, границ родителей, захвата мыши, порядка соседей
(включая `ToFront()` и `ToBack()`), активного диалога и окон поверх него
в текущем держателе. Если курсор попал в дочерний контрол, проверка родителя
тоже возвращает `true`. Перекрытый сосед возвращает `false`.

Проверка использует прямоугольники: прозрачные пиксели текстуры не учитываются.
Она не вызывает обработчики событий и не меняет фокус или захват мыши.

### Порядок контролов: ToFront и ToBack

```lua
local result = control:ToFront()
local result = control:ToBack()
```

| Метод | Результат |
| --- | --- |
| `ToFront()` | Контрол рисуется последним среди детей своего родителя, поверх соседей |
| `ToBack()` | Контрол рисуется первым среди детей своего родителя, под соседями |

Методы доступны у `CUIWindow` и наследующих его Lua-классов, перечисленных
для `AddSelfCallback`. Они не принимают другого родителя и не переносят контрол
между ветками дерева. Одинаковая глубина вложенности при разных родителях
не делает контролы соседними для этой операции.

Меняется отдельный порядок отрисовки, а не логический список детей. Родитель,
локальные координаты, размер, владение, подписки и порядок обновления сохраняются.
Раскладка `CUIStackPanel` и списка прокрутки продолжает использовать исходный
логический порядок элементов. Порядок проверки мыши соответствует новому
порядку отрисовки; изменение не поглощает события автоматически.

Возвращается `true`, если контрол принадлежит текущему родителю и операция
применима. Повторный вызов для уже крайнего контрола также возвращает `true`.
Если родителя нет или контрол не числится среди его детей, возвращается `false`.
Для корневого окна, добавленного непосредственно в holder, методы не меняют
очередь holder и возвращают `false`.

Перестановка видна при следующей отрисовке и учитывается последующими проверками
мыши. Уже начатый обход отрисовки или мыши продолжает работать со своим снимком
порядка. Вызов из `WINDOW_UPDATE` не меняет обход логического списка детей и
не добавляет обновлений. Новые дети по умолчанию добавляются поверх существующих.

Чтобы поднять целую ветку, можно вызвать `ToFront()` у её родительского
контейнера, если тот имеет своего родителя. Дети останутся в том же контейнере.
Методы не меняют внутренние слои, которые специальные C++-контролы рисуют
вручную вне списка прикреплённых детей.

## 6. Владение и выгрузка

| Объект | Кто владеет |
| --- | --- |
| `CreateScriptWindow()` | Lua; сохраняйте ссылку, пока окно зарегистрировано в UI |
| `CUIStatic()` без родителя | Lua; сохраняйте ссылку, пока статик зарегистрирован в UI |
| Статик из `InitNoXmlStatic(..., parent)` | Родитель; метод включает автоматическое удаление |
| Контрол после `SetAutoDelete(true)` и `AttachChild` | Родитель |
| `AddDialogToRender(window)` | Только регистрация; владение окном не передаётся |

Сначала снимайте окно с отрисовки или закрывайте диалог, затем освобождайте
Lua-ссылку. Не прикрепляйте один контрол повторно и не используйте ссылки на
дочерние контролы после удаления родителя. Переменная Lua со ссылкой на ребёнка
не продлевает жизнь объекта, которым владеет родитель.

### Автоматическая очистка при net_destroy и keep_lua

Автоматическая очистка работает в двух случаях:

- При уничтожении окна автоматически снимаются его регистрации из очередей
  отрисовки, отложенного добавления и стека получателей ввода.
- Перед `net_Destroy` текущего актора очищаются очереди игрового HUD. Очереди
  также очищаются при остановке уровня, выгрузке и уничтожении HUD.

Очистка не зависит от выгрузки Lua. При `keep_lua` существующие Lua-ссылки могут
пережить актора: окно скрывается и отключается, больше не обновляется и не
рисуется старым HUD, но не удаляется принудительно. Глобальные переменные Lua
движок автоматически не обнуляет. У интерактивных окон сбрасывается `GetHolder()`.

На новом уровне создайте окно заново либо обновите его ссылки на актора
и игровые объекты и явно добавьте в новый `get_hud()`. Сохранённый holder старого
HUD использовать нельзя. Очистка UI не отменяет собственные таймеры, подписки
и другие вызовы ваших скриптов, которые могут обращаться к старому актору.

Ручная очистка остаётся совместимой и полезна, когда нужно освободить Lua-ссылку
и связанные со скриптом ресурсы:

```lua
function remove_window()
    if window ~= nil then
        local hud = get_hud()
        if hud then
            hud:RemoveDialogToRender(window)
        end
        window = nil
    end
end

function actor_on_net_destroy()
    remove_window()
end
```

Функцию `actor_on_net_destroy` нужно подключить к существующему механизму событий
ваших скриптов; одно объявление функции не регистрирует событие автоматически.
Ручная очистка выполняется до уничтожения HUD и актора. Повторный
`RemoveDialogToRender` после автоматического снятия регистрации допустим.
Автоматическое снятие регистрации не означает передачу владения окном движку.

## 7. Диагностика

Для вывода диагностических сообщений используйте:

```lua
log1("UI test started")
```

В текущих исходниках `log` экспортируется условно для режима редактора, а
игровой `printf` выходит без вывода при отсутствии `log`. Поэтому отсутствие
сообщения от `printf` не подтверждает успешное выполнение.

Диагностика без общего необработанного Lua-исключения:

```lua
local ok, err = pcall(function()
    assert(GetCurrentDialogHolder(), "No active UI holder")
end)
log1(ok and "UI TEST: OK" or ("UI TEST ERROR: " .. tostring(err)))
```

## 8. Совместимость и проверка

Сохранены `InitStatic`, `Init3tButton`, `CUIScriptWnd`, наследование через
`class`/`super()`, существующие сигнатуры методов и четырёхаргументный
`AddCallback`. Новые события добавлены в конец C++-перечисления, чтобы не менять
числовые значения прежних событий.

Изменённые файлы проверены компиляцией.

Примеры и обработку событий нужно проверять в целевой игровой конфигурации.
Исправление очистки проверено компиляцией и временной локальной проверкой
производственных методов очередей: уничтожение окна до обновления, отложенные
добавления, удаление во время обновления и отрисовки, стек ввода, уничтожение
holder раньше окна и сохранение окна между двумя HUD, как при `keep_lua`.
Тестовые файлы и настройки CMake в репозиторий не добавлены. Полный сценарий
выхода с уровня с модом ещё нужно повторить в игре после пересборки.
Эти примеры описывают текущий API, а не результат завершённого игрового теста.

Изменена внутренняя структура `CUIWindow`; после этого исправления необходима
пересборка всех использующих её модулей движка. Смешивать старые и новые DLL нельзя.
