# Стиль кода (C++)

[English](./code-style-cpp.md) | Русский

Форматирование задаётся файлом [`.clang-format`](../.clang-format), именование — файлом [`.clang-tidy`](../.clang-tidy). Этот документ описывает оба файла и правила, которые инструменты не проверяют. Если документ расходится с конфигом, прав конфиг. Базовые паттерны (RAII, namespace или class, интерфейсы, платформенный код) описаны в [Coding Guidelines](https://ixray-team.github.io/ixray-1.6-stcop/main/coding-guidelines.html).

## Инструменты

- Перед коммитом форматировать изменённый код через `clang-format`. Visual Studio и VS Code подхватывают `.clang-format` из корня репозитория.
- Проверять имена через `clang-tidy` (`readability-identifier-naming`).
- Форматировать только тот код, который меняется. Не переформатировать целиком старые файлы в одном коммите с функциональными изменениями.

## Файлы

Принятые расширения:

- `*.cpp` для файлов исходного кода
- `*.h`/`*.hpp` для заголовочных файлов

Файлы должны сохраняться в кодировке UTF-8 с окончанием строк CRLF и должны заканчиваться одной пустой строкой

Новые комментарии следует писать с использованием английского языка

Для названий новых файлов должен использоваться PascalCase, для существующих ранее должен использоваться тот стиль, который уже был принят в библиотеке или проекте

## Комментарии

- Заголовки файлов не используются в проекте, однако следует при необходимости вставлять описание файла в начале:

  ```cpp
  // Описание файла
  ```

- Допускается сообщение о недоработанной функциональности вида `// TODO: Описание`
- Допускается сообщение о баге вида `// BUG: Описание`
- Если добавлен костыль или хак, то необходимо сообщить об этом в комментарии вида `// HACK: Описание`

## Инклуды

- Не использовать старые include guards
  - Использовать `#pragma once` вместо них
- Все инклуды должны располагаться до основного кода вверху файла и должны быть сгруппированы в следующем порядке:

  ```cpp
  // Предкомпилируемый хедер
  #include "stdafx.h"

  // Внутреннее API
  #include "xrCore.h"
  ```

- `clang-format` не сортирует инклуды (`SortIncludes: Never`). Порядок задаётся вручную: предкомпилируемый хедер всегда первый, порядок внутри группы сохраняется, так как от него зависят некоторые хедеры

## Именование

`.clang-tidy` требует PascalCase (в терминах clang-tidy — `CamelCase`) почти для всех имён:

| Сущность | Стиль | Пример |
|----------|-------|--------|
| Классы, структуры, перечисления | PascalCase | `class SceneLoader`, `enum class LoadMode` |
| Пространства имён | PascalCase | `namespace NameUtils` |
| Функции и методы | PascalCase | `void GenObjectName()` |
| Локальные, глобальные и статические переменные | PascalCase | `u32 ObjectCount` |
| Поля классов и структур (с любым доступом) | PascalCase | `u32 RefCount` |
| Константы, `constexpr`, элементы перечислений, `const` параметры | PascalCase | `constexpr u32 MaxObjects`, `LoadMode::Append` |
| Макросы | UPPER_CASE | `#define IXR_WINDOWS` |

- Уже существующие ранее названия публичных и защищённых функций, методов и классов следует оставлять как есть для сохранения совместимости API
- Допустимые префиксы перед именем в PascalCase:
  - `I` для интерфейсов: `IReader`
  - `C`, `E`, `F` в старых именах типов: `CRenderDevice`, `EScene`. Новым типам они не нужны
  - `g_` для глобальных объектов: `u32 g_ObjectCount;`
  - `xr_` для IXR-алиасов стандартных типов и функций: `xr_vector`, `xr_strcpy`
- Названия интерфейсов должны начинаться с префикса `I`
- Названия полей не используют префиксы `_` и `m_`:

  ```cpp
  class SomeClass
  {
  public:
      u32 GetValue() const
      {
          return Value;
      }

  private:
      u32 Value = 0;
      u64 TotalSize = 0;
  };
  ```

- Названия параметров тоже пишутся в PascalCase. `clang-tidy` проверяет только `const` параметры, но стиль для всех один
- Названия логических переменных должны начинаться с глагола:

  ```cpp
  bool HasChildren;
  bool IsEnabled;
  ```

- Названия объектов лямбда-функторов должны заканчиваться постфиксом `Lambda`

  ```cpp
  auto AddLambda = [](auto A, auto B)
  {
      return A + B;
  };
  ```

- Однобуквенные имена тоже пишутся с большой буквы (`I`, `T`). Вместо счётчика цикла лучше использовать range-based `for` или описательное имя (`Index`)
- Названия параметров шаблонов должны иметь описательные имена, если только однобуквенное имя не говорит само за себя, а описательное имя не добавит ценности
- Следует рассмотреть возможность использования названия `T` в качестве названия параметра шаблона, если используется один параметр
- Следует добавлять к названиям параметров шаблонов префикс `T`

## Стандартная функциональность

- Следует использовать X-Ray типы, контейнеры и функции вместо стандартных
  - Код, который выполняется до `Memory._initialize` (старт процесса, обработка исключений), использует контейнеры `std::`
  - Если X-Ray аналога нет, допускается стандартный тип, контейнер или функция. Для часто используемых следует объявить алиас:

  ```cpp
  using xr_string_view = std::string_view;
  ```

## Приведение типов

- Приведения в стиле C разрешены и более предпочтительны, чем `static_cast`
- Использовать `smart_cast` вместо `dynamic_cast` если `smart_cast` доступен

## Платформозависимость

Платформозависимый код находится в `Platform`-реализациях (`Windows`, `Linux`, `macOS`) за общим интерфейсом. Игровые, рендерные и другие платформонезависимые модули не подключают платформенные заголовки и не используют платформенные API.

Условная компиляция допускается только внутри платформенного кода или когда различие нельзя вынести за интерфейс. В условии используется один из допустимых макросов:

- `IXR_WINDOWS`
- `IXR_LINUX`
- `IXR_APPLE_SERIES`
- `IXR_BSD_SERIES`

## Форматирование

Правила ниже применяет `clang-format`. В примерах для читаемости используются пробелы, в коде отступы делаются табуляцией.

### Отступы и строки

- Отступы — табуляцией, одна табуляция равна 4 колонкам (`UseTab: Always`, `IndentWidth: 4`)
- Ограничения длины строки нет (`ColumnLimit: 0`). `clang-format` не переносит длинные строки, их следует разбивать вручную там, где это улучшает читаемость
- Не больше 2 пустых строк подряд
- Блок не начинается с пустой строки
- Указатели и ссылки прижимаются к типу: `int* Ptr`, `const xr_string& Name`

### Фигурные скобки

- Фигурные скобки всегда на новой строке (стиль Allman), в том числе у функций, классов, пространств имён и лямбд
- Фигурные скобки обязательны для каждого `if`, `else`, `for`, `while` и `do`, даже для одной инструкции. `clang-format` расставляет недостающие сам (`InsertBraces: true`)
- `if`, циклы и блоки никогда не пишутся в одну строку
- Короткую функцию можно записать в одну строку, только если она определена в теле класса:

  ```cpp
  class SomeClass
  {
  public:
      u32 GetValue() const { return Value; }
  };

  u32 SomeClass::GetSize() const
  {
      return Size;
  }
  ```

- Между ключевым словом и условием должен быть 1 пробел
  - В диапазонных выражениях двоеточие должно быть выделено с двух сторон

  ```cpp
  if (...)
  {
      ...
  }
  else
  {
      ...
  }

  for (...)
  {
      ...
  }

  while (...)
  {
      ...
  }

  for (auto Value : SomeCollection)
  {
      ...
  }

  for (auto& [Id, Name] : SomeMap) // Вместо `for (auto It : SomeMap)`
  {
      ...
  }
  ```

### Классы

- Модификаторы доступа находятся на одном уровне с ключевым словом `class`, перед ними пустая строка
- Наследуемые классы и интерфейсы пишутся либо в одну строку, либо, при разбиении, перенос делается после двоеточия и каждый базовый класс на своей строке:

  ```cpp
  class SomeClass :
      public IInterface,
      public BaseClass
  {
  public:
      SomeClass();

  private:
      u32 Value = 0;
  };
  ```

- Список инициализации конструктора начинается с новой строки с двоеточия:

  ```cpp
  SomeClass::SomeClass(u32 Value, u32 Size)
      : Value(Value), Size(Size)
  {
  }
  ```

### Вызовы и объявления функций

- Аргументы и параметры пишутся либо все в одну строку, либо каждый на своей строке. Во втором случае перенос делается после открывающей скобки, а закрывающая скобка стоит на отдельной строке:

  ```cpp
  DoSomething(FirstArgument, SecondArgument, ThirdArgument);

  DoSomething(
      FirstArgument,
      SecondArgument,
      ThirdArgument
  );
  ```

### Операторы

- Тернарный оператор разрешён на одной линии
  - При более сложном условии или результате он разбивается по строкам, перенос делается перед `?` и `:`

  ```cpp
  auto Result = IsEnabled ? GetValue() : 0;

  auto Result = HasChildren
                    ? CalculateChildrenSize(Node, Flags)
                    : CalculateOwnSize(Node);
  ```

- Операторы ветвления должны следовать шаблону
  - Метки `case` имеют отступ внутри `switch`
  - `case` записывается либо в одну строку (`AllowShortCaseLabelsOnASingleLine: true`), либо блоком в фигурных скобках. Тело `case` на нескольких строках без скобок запрещено
  - Открывающая скобка стоит на строке после метки, `break` и `return` находятся внутри скобок
  - Несколько меток с общим телом идут друг за другом, каждая на своей строке

  ```cpp
  switch (Condition)
  {
      case LoadMode::Append: AppendObjects(); break;
      case LoadMode::Replace: ReplaceObjects(); return;

      case LoadMode::Merge:
      case LoadMode::Update:
      {
          u32 Count = GetCount();
          Process(Count);
          break;
      }

      default: break;
  }
  ```

## Запреты

- Следует группировать свойства, геттеры/сеттеры, методы, конструкторы/деструкторы по модификаторам доступа в указанном порядке
- Следует использовать `using` вместо `typedef` там, где это возможно
- Запрещены для использования: `malloc`, `calloc` и `realloc`. Вместо этого следует использовать `xr_alloc`
- Для выделения памяти используется оператор `new`, для освобождения памяти используется оператор `xr_delete`, который автоматически приводит указатели к `nullptr`
- Запрещены исключения C++ в любой форме
  - Следует избегать использования обработки исключений в стиле C, если это не обсуждено с командой или сопровождающим проекта
- Запрещено использование множественного наследования классов
- Объявление метода как `const` является обязательным, если он не изменяет поля класса
  - Константные переменные не являются обязательными
- Функция должна пытаться принимать параметры по ссылке, а не обрабатывать типы, превышающие машинное слово (8 байт)
- Переопределяемые виртуальные методы должны быть указаны с помощью ключевого слова `override`

  ```cpp
  virtual void SomeFunc() override;
  ```

- Следует использовать `nullptr` вместо `NULL`, а также следует использовать `nullptr` для проверок
- Использование строго типизированных перечислений (`enum class`) должно быть везде, где это возможно
- Запрещено использование анонимных перечислений и структур
- Запрещены безымянные пространства имён (`namespace { ... }`) и безымянные структуры (`struct { ... } Value;`). Пространству имён следует давать имя, а внутренние вспомогательные функции объявлять как `static`:

  ```cpp
  // Вместо `namespace { bool ParseIndex(...); }`
  static bool ParseIndex(const char* Str, u32& Index);

  // Вместо `struct { u32 Min, Max; } Range;`
  struct IndexRange
  {
      u32 Min = 0;
      u32 Max = 0;
  };

  IndexRange Range;
  ```
- Следует избегать большой вложенности кода
- Следует всегда определять конструктор и деструктор
- Прямое полное включение пространства имён в стиле `using namespace` запрещено
- Следует использовать ключевое слово `final` для классов, которые не имеют наследников
- Следует использовать ключевое слово `auto` только в том случае, если инструмент может однозначно вывести тип из выражения
- Следует использовать ключевое слово `default` там, где это возможно
- Следует использовать ключевое слово `delete` для виртуальных функций
