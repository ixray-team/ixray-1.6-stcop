# Новая система сохранения

> [!IMPORTANT]
> **Минимальная версия**: 1.5

## Нововведения

В качестве альтернативы сохранения данных в нетпакетах или LuaMarshal добавлена новая система сохранения данных, которая закрывает следющие проблемы нетпакетов:

* Повреждение сохранений при изменении набора данных или их порядка, что требовало ручной обработки
* Почти полное отсутствие механизмов отладки и поиска причины "битья" сейвов
* Невозможность смешивать чанки и обычные данные без ручной обработки

Помимо этого, сделаны следующие фичи:

* Двусторонние функции сериализации данных
* Механизмы записи в чанки и массивы используя RAII подход
* Некоторые механизмы сжатия данных без потерь
* Асинхронная запись сохранения на диск

> [!IMPORTANT]
> Новая система сохранения полностью несовместима со старой, а также подходами с редактированием данных в нетпакетах! Для использования системы необходимо не только включить её, но и пересобрать спавн. В составе xrFilesConverter есть конвертер спавна из ванильного формата в новый, однако обратного не предусмотрено. В SDK, однако, поддерживается загрузка локаций с ванильным вариантом системы сохранений, но важно отметить, что сохранённый спавн в IX-Ray SDK с использованием новой системы сохранений несовместим с другими СДК без поддержки этой системы!

Чтобы включить новую систему сохранений, нужно в engine_external.ltx в секции system выставить значение true в поле AdvancedSerialization:

```ini
[system]
AdvancedSerialization = true 
```

После чего пересобрать в СДК спавн для всех локаций мода и собрать новый all.spawn.

## Система чанков

Система чанков, доступная в нетпакетах, была значительно доработана, позволив не только смешивать данные и чанки, но и в целом облегчить жизнь при написании функций сериализации.
Для мододела доступны следующие функции и типы в скриптах:

* Методы `Serialize` у биндеров, клиентских и серверных объектов - основная функция, через которую происходит чтение и запись данных
* Тип `SaveObject` - прокси-объект, который выполняет запись и чтение данных из сейва

У типа `SaveObject` есть следующие методы:

* `HasChunk` - Функция проверки наличия субчанка в текущем чанке. Может применяться и при сохранении, но в первую очередь при загрузке. Принимает тип `String` (Имя), возвращает тип `bool` (наличие).
* `ForChunk` - Функция, которая пытается войти в чанк с желаемым именем. Если это загрузка и она нашла субчанк, то найденный субчанк становится активным и выполняется функция, переданная вторым аргументом, иначе просто ничего не делает. Если это сохранение, то создаёт чанк с переданным именем и вызывает переданную функцию. После окончания работы функции выходит из субчанка. Принимает тип `String` (Имя) и функцию сериализации.
* `ForArray` - Функция-близнец `ForChunk`, но помечает следующую область как массив. Рекомендуется в случае, если нужно сохранить массив однотипных данных. Принимает только функцию обработки массива.
* `s_vec3` - Функция сохранения вектора
* `s_float` - Функция сохранения вещественного числа
* `s_u64` - Функция сохранения `uint64_t`
* `s_s64` - Функция сохранения `int64_t`
* `s_u32` - Функция сохранения `uint32_t`
* `s_s32` - Функция сохранения `int32_t`
* `s_u16` - Функция сохранения `uint16_t`
* `s_s16` - Функция сохранения `int16_t`
* `s_u8` - Функция сохранения `uint8_t`
* `s_s8` - Функция сохранения `int8_t`
* `s_bool` - Функция сохранения `bool`
* `s_stringZ` - Функция сохранения строки. Настоятельно рекомендуется не пытаться сохранять огромную строку, и использовать вместо этого string table
* `IsSave` - Функция проверки того, какая сейчас происходит операция, сохранение или загрузка. Позволяет написать логику, которая должна сработать только при сохранении или только при загрузке. Возвращает `bool` (если сейчас сохранение).

```lua
function my_class:Serialize(Object)
    Object:ForChunk("my_class", function()
        Object:ForChunk("other_chunk", function()
            -- другие данные
        end
        my_u8 = Object:s_u8(my_u8) -- Записывает значние в себя при сохранении и возвращает его при загрузке
        Object:ForArray(function()
            if Object:IsSave() then
                Object:s_u32(#my_array)
                for k,v in pairs(my_array) do
                    -- Сохранить
                end
            else
                local size = 0
                size = Object:s_u32(size)
                for i in 1,size do
                    -- Загрузить
                end
            end
        end)
        if Object:HasChunk("check_chunk") then
            -- что-то
        end
    end)
end
```

Возможно безопасно делать вложенные чанки и смешивать их с простыми данными. При необходимости сделать аддон или патч, который затрагивает сохранения, крайне рекомендуется создать новый чанк внутри функции (можно внутри другого чанка) и записывать там новые сериализуемые данные, а старые данные, которые нужны для совместимость, пометить условием `not Object:IsSave()`. И главное - не требуется вручную хранить позиции записи, за вас позаботится система.

## Валидация

Одна из крупных проблем нетпакетов - очень малое число механизмов для валидации данных. В новой системе все данные (чанки, массивы, примитивы) автоматически помечаются, что позволяет не просто при загрузке данных делать проверку на корректность чтения, но и даже в процессе сохранения сразу получать сообщение, если скрипт сериализации по какой-то причине не отработал должным образом. Теперь вместо тихой поломки сейчас, а потом ломание игрового прогресса в будущем в совсем другом месте игрок будет получать сразу конкретную ошибку - решайте сами, что хуже.
Числовые данные валидируются ещё и по диапазону. Например, для uint8_t максимальное значение 255, и при попытке записать туда 1000 вместо того, чтобы записать некорретное значение, будет выдана ошибка. Однако, при загрузке сохранения есть возможность автоматического приведения чисел в больший диапазон. Например, если раньше данные сохранялись как uint16_t, а теперь мы хотим их читать как uint32_t, то система корректно сама обработает эту ситуацию, выдав ровно то, что нужно, не поломав другие данные.

## Оптимизации

К сожалению, фичи новой системы не остались без недостатков. Система несколько сложнее нетпакетов, что незначительно (почти незаметно) сказалось на скорости сохранения и в большей мере на вес файла. Поэтому были введены следующие внутренние механизмы сжатия данных:

* Двуэтапный процесс сохранения - для ситуаций, когда это можно позволить, было выделено два этапа сохранения: сбор данных и запись на диск. В то время, как сбор данных остался синхронным ввиду невозможность выделить его, этап записи полностью независим от основного потока игры. Благодаря этому даже в случае, если в компьютере находится медленный диск, сохранение не будет приводить к провисанию.
* Квантование чисел без потерь - то, что было невозмножно автоматически в нетпакетах, легко было реализовано в новой системе благодаря маркировке данных. Теперь в случае, если мы записываем число с большим диапазоном, но само значение числа мало, оно сразу сжимается в минимально возможный тип. Так, например, если мы хотим сохранить число 10 как uint64_t, то оно будет сжато до 2 байтов (1 байт маркировки + 1 байт данных) вместо 9 байтов в обычной ситуации.
* Сжатие булевых переменных - все булевые переменные в новой системе сжимаются в битовые поля, благодаря чему затраты памяти на их хранение уменьшаются в 8 раз.
* Пул строк - все строки в новой системе сохранения используют пул вместо банальной записи. Это позволяет не хранить кучу копий одной строки, а хранить строку 1 раз, подставляя идентификаторы на их место. Однако, если строка слишком большая (что сразу считается ошибкой), она не будет использовать пул, а сразу будет записываться на месте.
