# Ведение документации IX-Ray Framework

Эти инструкции предназначены для ИИ-агентов, которые пишут или обновляют пользовательскую документацию этого раздела. Существование карты не означает задачу на изменение кода Framework или массовое переписывание справочника.

## Назначение и источники

Документация объясняет, как использовать публичное API. Описывай задачу, доступные функции, аргументы, результаты и рабочий пример. Внутренняя архитектура, история разработки, устройство VM и ход отладки относятся к техническим материалам и картам агентов, если они не нужны пользователю для правильного вызова.

Перед изменением страницы:

1. Прочитай соответствующую карту AGENTS.md со стороны скриптов, существующую страницу и связанный пример.
2. Проверь реальную сигнатуру, публичную обёртку, значения по умолчанию, результаты и место вызова. Старую документацию используй как образец оформления, а не как доказательство поведения.
3. Сохраняй актуальные правила владельца проекта. Например, техническая возможность обратиться к модулю по имени файла не разрешает показывать такое обращение игровому коду.
4. Не исправляй реализацию только ради соответствия старому тексту. Выявленное расхождение фиксируй в рамках поставленной задачи; не включай несвязанные исправления молча.

Для изменения только описания существующего метода новая страница и перестройка навигации не нужны.

## Формат страницы

Сохраняй оформление соседних страниц и синтаксис VitePress:

1. Название Framework/фичи и подходящий заголовок раздела.
2. Блок `> [!IMPORTANT]` с `Статус` и `Минимальная версия`, строка статуса заканчивается `<br>`.
3. Короткое описание применимости и список документируемых публичных функций.
4. Раздел `Описание методов` с сигнатурами, `args` и `retval`.
5. Раздел примеров использования.

Минимальную версию и статус бери из подтверждённой информации. Не назначай всем страницам версию текущей задачи, не выдумывай дату появления API и не меняй статус без основания. Если отдельный метод появился позже базового API страницы, укажи подтверждённую версию именно для него.

Образцы оформления: [кеш](utils/ffx_cache_utils.md), [опции](modules/ixr_options.md), [сигналы](modules/ixr_signals.md), [модули](modules.md). Переноси структуру оформления, но не возможные неточности типов или формулировок.

## Описание каждой функции

- Начинай с короткого `--//` комментария: что делает вызов и в каком случае он нужен.
- Пиши точное имя и позиционную сигнатуру. Сохраняй регистр, существующие названия и соглашение `.`/`:`. Не исправляй публичное имя ради красоты.
- В `args:` перечисляй параметры в порядке вызова: `name (type)(required|optional) - описание`.
- Для optional указывай реальное значение по умолчанию и способ пропустить аргумент. Не путай omitted, `nil`, `false` и пустую таблицу.
- Для времени указывай единицы, для индекса — базу отсчёта, для вектора/объекта — назначение и допустимость отсутствия. Для таблицы опиши ожидаемые поля или структуру массива.
- В `retval:` укажи фактические типы и смысл каждого результата, в том числе `false`, `nil`, пустую таблицу и отсутствие результата. Не обозначай декодированную таблицу как string только потому, что вход был строкой.
- Если один аргумент меняет форму результата, опиши варианты отдельно. Пример принципа: выбор одного имени может возвращать само значение, выбор списка — массив записей.
- Ошибки, fallback/default и побочные эффекты описывай в объёме, необходимом для правильного использования. Не обещай подавление ошибок, сохранение данных или строгую типизацию, если реализация этого не обеспечивает.
- Указывай контекст данных: вызывающий скрипт, объект, shared-область; область действия настройки и необходимые события готовности.
- Callback описывай как самостоятельную сигнатуру: порядок аргументов, момент и кратность вызова, условия готовности и смысл результата/изменяемой таблицы.

Образец блока сигнатуры из существующего API:

```lua
--// Удалить закешированное значение по ключу.
invalidate_cache(key_name)
args:
  key_name (string)(required) - ключ кеша для удаления.
retval: (none)
```

Такие блоки являются справочным описанием, а не исполняемым Lua: `args`/`retval` не нужно добавлять в рабочий скрипт. Для исходного расположения используй существующий формат ограждения `lua [gamedata\scripts\...]`. При использовании `::: code-group` закрывай его парным `:::` после кодовых блоков.

## Принцип примеров

Показывай полезные сочетания существующих механизмов и объясняй, почему они подходят задаче. Пример: `IsActionThrottled` как лёгкая альтернатива отдельному таймеру для редкого выполнения работы внутри уже существующего update. В таком примере проверка вызывается часто, работа — реже; самостоятельного отложенного вызова нет. Не называй отсечку полноценной заменой всех возможностей таймеров и не обещай точной периодичности независимо от частоты update. Модуль таймеров показывай прежде всего на сюжетных/игровых сценариях, которым нужно сохраняемое состояние: система сохранения недешёвая и не предназначена для повсеместного технического throttling. Примеры модуля триггеров должны относиться к геймплейным/сюжетным пространственным зонам, а не к универсальным внутренним проверкам скриптов.

- Показывай минимальный законченный сценарий, который решает пользовательскую задачу. Избегай несуществующих помощников и неописанных функций-заглушек. Если это схема, явно обозначь её и объясни заменяемые части.
- В примере должны быть видны получение API, подходящая точка входа, вызов и наблюдаемый результат. Для простого преобразования достаточно входа и результата; для события нужен пример подписки.
- Пользовательский код вне Framework использует глобальные методы из `ixray_system/global.lua`, методы событий из `dynamic_callbacks.lua` и API, явно предоставленный callback. Не показывай прямой доступ к внутренним таблицам и менеджеру Framework.
- Для `GetModule`, `IsModuleLoaded`, `ClosureModuleIsExists` используй только alias. Имена файлов допустимы в предназначенном для подключения модулей `configure`.
- Для опций образец — `gamedata/scripts/example_options/ixr_options_template.script`: метаданные в `on_game_start`, регистрация через замыкание на `on_init_ixr_options`, получающее `_ref`. Захват `_ref` во вложенном обработчике является легитимным доступом; не заменяй его поиском внутреннего модуля.
- Новое событие регистрируется только в публичном `__ixr_override_signals_intercepts.script`. Его список аргументов — подсказки для мододела, а не строгие имена игровых типов. В подписке сохраняй позиционный порядок; неоднозначным параметрам дай понятные имена.
- Учитывай жизненный цикл: при `on_game_start` не обещай готового `db.actor`; при работе с хранилищем — загруженных данных без проверки соответствующего этапа.
- Общие утилиты и библиотеки не ограничивай сценарием аддона. Они используются и оригинальными скриптами, и Framework, и модами.
- Для необязательного аргумента, ошибок или важной особенности добавь отдельный короткий пример только если он помогает понять контракт. Не размножай одинаковые вызовы с заменёнными числами.
- Не запускай игру, отладчик, сетевое соединение, запись пользовательских опций или очистку журналов ради составления документации. Если пример не проверялся выполнением, не объявляй его проверенным в игре.

## Документирование интеграционных обвязок аддонов

Канонический шаблон добавления вызова или дополнительного кода аддона: в нужном месте общей функции отправить событие со **всеми необходимыми аргументами**, а реализацию разместить в отдельном обработчике аддона через `RegisterScriptCallback`. Передавай нужные объекты, значения, таблицы контекста и, если требуются, ссылки на функции-помощники; не заставляй аддон искать приватные данные или обращаться к внутренностям Framework. Общий исходник не должен напрямую зависеть от имени скрипта аддона, проверять наличие его конкретного метода или содержать его специфическую логику. При отсутствии подписчика дополнительный вызов просто не выполняется, и ванильная функция продолжает стандартную работу без ожидания ответа. Если требуется не дополнение, а замена ветки, явно предусмотри соответствующий слот функции/флаг и исходную ветку по умолчанию. Новое имя события регистрируется только в `__ixr_override_signals_intercepts.script`; каталог описывает порядок и назначение переданного контекста.

Канонический шаблон изменения значения через аддон: **до события** создать таблицу с исходным значением по умолчанию → передать её в событие → подписчик при необходимости меняет поле этой же таблицы → после отправки исходный код читает поле. Значение по умолчанию соответствует ванильному расчёту, а не произвольной заглушке. Если подписчика нет, таблица остаётся неизменной и используется ванильный результат. Пример существующего контракта: `local flags_table = {new_price = price}` перед событием изменения цены; после события — `price = flags_table.new_price`. Для такого механизма не передавай только отдельное число/строку/boolean в надежде изменить переменную вызывающего кода: изменяемым контейнером служит таблица.

Первым условием описывай сохранение ванильного поведения без аддона. Пример должен быть корректен с нулём подписчиков и после отключения/удаления аддона: исходный код использует стандартный результат или исходную ветку и не ждёт ответного события, флага готовности либо последующего действия необязательной части. Не показывай примеры, превращающие опциональное расширение в обязательную зависимость ванильной механики.

События могут предоставлять точку расширения ванильной логики, а не только уведомление. Для такого API показывай обе стороны: небольшую точку `SendScriptCallback` в общем исходнике и отдельную подписку аддона через `RegisterScriptCallback`. Специфический код остаётся у аддона; стандартное поведение без подписчика сохраняется.

- Укажи место относительно исходного действия: до расчёта, после расчёта, перед проверкой, вместо стандартной ветки или после побочного эффекта.
- Опиши позиционные аргументы, исходные поля контекста и какие из них разрешено менять; покажи, где вызывающий код использует результат.
- Если в таблицу записывается функция, отдельно опиши её сигнатуру и момент вызова, передаваемые локальные данные/помощники и нужный результат. Установка функции подписчиком и её вызов исходным кодом — разные этапы.
- Покажи изменение полей той же таблицы, а не переприсваивание локального параметра. Не обещай отмену действия через `return false` подписчика: шина его результат не собирает.
- Отметь стандартное поведение без изменения контекста, синхронность и отсутствие гарантированного порядка нескольких подписчиков.
- Используй существующие примеры `inventory_upgrades`, `death_manager`, `xr_motivator`, `surge_manager`. Сверяй фактические аргументы функции-замены с её местом вызова, а не только с краткой подсказкой в каталоге.
- Новое имя события по-прежнему регистрируется только в `__ixr_override_signals_intercepts.script`. Не представляй обвязку как необходимость копировать ванильную функцию или менять ядро Framework.

## Обновление справочника

- При изменении API обновляй связанную сигнатуру, описание аргументов, результаты, примеры и ссылки вместе. Проверяй, не используется ли этот контракт на другой странице.
- Сохраняй разделение пользовательской документации и AGENTS.md: первая учит использовать API, вторые помогают агенту найти реализацию и соблюдать границы изменений. Не дублируй целиком справочник в карты.
- Не добавляй неподтверждённые обещания производительности, поддержки любых типов, автоматической сериализации или порядка вызовов. Не представляй обычную таблицу флагов как потоковый mutex.
- Сохраняй локальный стиль Markdown, блоки VitePress, относительные ссылки и существующие имена файлов. Не переименовывай разделы и не форматируй весь справочник ради небольшого дополнения.
- Для изменения только инструкций достаточно проверить наличие связанных файлов и корректность ссылок. Для опубликованной страницы с новым Markdown/VitePress оформлением используй существующие проверки сайта; не выдумывай результат сборки.
