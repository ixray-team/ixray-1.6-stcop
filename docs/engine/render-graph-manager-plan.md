## 1. Цель

Сборка графа должна быть **одним механизмом, который работает для чего угодно**: основной сцены, каскадов, дождя, SSLR, теней прожекторов. Новый проход — это новое описание вида, а не новая копия кода.

В `RenderGraphManager` это устроено так: граф — объект вида, у него один и тот же цикл `traverse` → `capture_*` → `render_*`, а отличия заданы параметрами (`CDSGraphManager GMRainWet`, `GMBase`, `GMRefl`, `cascade.GMCascade`, `light.GMLight`).

## 3. Целевая модель

Описание вида — снимок всего, что нужно сборке. После `Begin` сборка не читает `Device`, `Environment`, `RImplementation.phase` и не зависит от того, на каком потоке идёт.

```cpp
struct GraphView
{
	u32 Phase;                      // PHASE_NORMAL, PHASE_SMAP, PHASE_REFLECT
	IRender_Sector* Sector;
	CFrustum Frustum;
	Fmatrix Transform;
	Fvector Origin;                 // точка обхода порталов
	u32 TraverseOptions;            // VQ_HOM, VQ_SSA, VQ_FADE
	ESPATIAL_TYPE DynamicTypes;
	bool PassMask[3];               // deferred, forward, wallmarks
	bool DepthOnly;                 // сейчас глобальный RImplementation.ZPrefill
	CObject* Ignore;

	// Снимок камеры и окружения, заменяет R_CullTLS и чтение Device
	Fvector CameraPosition;
	float Fov, FogDistance, FarPlane;
	float SsaDiscard, SsaLodA, SsaLodB;
};

class R_dsgraph_structure
{
public:
	void Begin(const GraphView& View);   // очистка и единая настройка вида
	void Traverse();                     // порталы, один раз за сборку
	void CollectDynamic();               // объекты, запуск SkeletonBatch
	void CaptureStatic();
	void CaptureDynamic();               // Wait, renderable_Render(this)
	bool IsSectorVisible(const CSector* Sector) const;

	void r_dsgraph_render_static(u32 Priority, bool Clear = true);
	void r_dsgraph_render_dynamic(u32 Priority, bool Clear = true);
	void r_dsgraph_render_graph(u32 Priority, bool Clear = true);   // обе части
};
```

Экземпляры отличаются только описанием:

| Граф | Фаза | Геометрия | Поток сборки |
| --- | --- | --- | --- |
| `GraphMain` | NORMAL | всё, HUD | основной |
| `GraphSun[3]` | SMAP | статика на воркере, динамика позже | `PreRenderThread` |
| `GraphReflection[6]` | REFLECT | статика | `PreRenderThread` |
| `GraphRain` | SMAP | статика | `PreRenderThread` |
| `GraphShadow` | SMAP | всё | основной, позже можно на воркер |
| `GraphZPrefill` | SMAP, `DepthOnly` | приоритет 0 | основной |

**Запуск на воркере** тоже один: `CollectGraphs` проходит по списку заявок «граф + описание», вместо `CollectReflections` и `CollectSunCascades` с их тикетами. Перед отрисовкой остаётся одна точка объединения: это конец сборки, а не простой.

**Интерфейс с игрой.** Передача `graph` уже сделана, поэтому оставляем её. Отдельно можно заменить `void*` на типизированный указатель и убрать умолчание `nullptr`, которое молча отправляет объект в `GraphMain`. Сейчас `nullptr` передают только HUD и UI (`player_hud.cpp`, `CutsceneItem.cpp`, `UI3dStatic.cpp`), так что это не срочно.

## 4. Убрать ожидание каскадов

На профайлере `Collect Sun Cascades` простаивает весь `OnFrame`. Причина: `PreRenderThread` стартует до `FrameMove`, а матрицы каскадов публикуются позже, из `CRender::Render` (`r4_R_render.cpp:507`). Отражения этого не делают: `BeginReflectionCollect` снимает камеру до старта потока (`device.cpp:237`).

**Что делаем:** считаем матрицы и публикуем заявку до `PreRenderThread.Run()`, как у отражений. `sun_ticket`, `EnsureSunCollect` и `wait` в начале `collect_sun_cascades` удаляются.

Что надо учесть при переносе, все пункты найдены в коде:

1. **Сборка читает глобальную камеру.** `CalcSSA`, `IsValuableToRender`, `FullDetailRejectStatic`, туман и выбор MU-лода берут `Device.vCameraPosition`, `Device.fFOV`, `CurrentEnv` прямо во время `OnFrame`, который их меняет. Поэтому снимок `GraphView` (этап 1) идёт **до** снятия ожидания. Отражения уже сейчас читают эти поля параллельно с `OnFrame`, и снимок заодно это исправит.
2. **`dwFrame`.** `FrameMove` увеличивает его после публикации. `prepare_sun_cascade_xforms` сравнивает `LastSunUpdateFrame != Device.dwFrame` (`R_sun.cpp:337`), а `LastSunUpdateFrame` записывается при отрисовке (`:580`). При простом переносе условие станет ложным и кэш солнца не будет обновляться. Нужно передавать номер целевого кадра.
3. **`BeginSunShadowFrame`** (`r4_R_render.cpp:505`) переносится вместе с публикацией.
4. **Ранние выходы `Render`.** Меню, `m_bFirstFrameAfterReset`, статическое освещение теперь известны только после старта сборки. Условие запуска надо проверять заранее. Лишняя сборка безвредна: граф очистится следующей.
5. **Матрицы отстают на кадр от камеры.** Accum использует те же `Cascade.xform`, поэтому рассогласования нет, сдвигается только покрытие. Кэш солнца и так живёт со старыми матрицами. Проверить резкий поворот и телепорт.
6. **`g_StaticTraversalStats.Current`** читается в сборке из любого потока (`r__dsgraph_build.cpp:930, 1039`). Счётчики сборки с воркера не должны попадать в статистику основного вида.

**Выгрузка и сброс.** Нынешнее ожидание заодно защищало от `disconnect` и `vid_restart`: оба идут внутри `FrameMove` и удаляют то, что читает сборка. Вместо покадрового лока `level_Unload` и `reset_begin` один раз вызывают `PreRenderThread.Wait()`. Кадры без выгрузки ничего не ждут.

**Лок со стадией уничтожения.** На этапах 1–2 не вводится. `CObjectList::Update` уничтожает объекты в `xr_object_list.cpp:263-317`, и когда воркер пойдёт по динамике, эта секция должна будет взять `xrSRWLock` эксклюзивно, а сборка — на чтение, пока работает с объектами.

Текущая сборка каскадов на воркере только статическая: сектора, порталы и визуалы уровня живут дольше объектов. Поэтому в ней лок ничего не защищает, держать его на всю сборку незачем, иначе кадры с уничтожением будут ждать воркер. Модели и частицы и так чистятся до старта потока (`device.cpp:205-215`).

**Открытый вопрос про динамику.** Лок защищает от удаления, но не от изменения. `CObjectList::Update` в том же `OnFrame` двигает объекты и анимацию, так что сбор динамики параллельно с ним может прочитать `XFORM` и кости посреди обновления. Поэтому `append_sun_dynamics` остаётся после `OnFrame`, пока отдельный замер и анализ на этапе 8 не покажут обратное.

## 6. Этапы

Каждый этап собирается, запускается и даёт ту же картинку, кроме отмеченных.

### Этап 0. Эталон

Снять через `-autotest` и фиксированные камеры: время кадра, захват профайлера, draw call на проход, скриншоты. Сценарии — в разделе 7.

### Этап 1. Снимок вида

**Сделано, не закоммичено.** `GraphView` хранит снимок вида, `R_CullTLS` удалён. Сборка читает его через аксессоры с проверкой `OwnsView`. `GraphMain` снимка пока не имеет и читает живые значения: `UI3dStatic` подменяет камеру на время иконок. Эта ветка уйдёт на этапе 6. `ZPrefill` остаётся глобальным до этапа 5: его читает только `GraphMain`.

**Готово, когда:** функции сборки не читают `Device`, `CurrentEnv`, `RImplementation.phase`.

### Этап 2. Снять ожидание каскадов

**Сделано, не закоммичено.** Раздел 4. Каскады публикуются до `PreRenderThread.Run()`, единственное ожидание — объединение в `render_sun_cascades`. Редактор и непредвиденные кадры собираются синхронно на основном потоке.

Замер встроенным профайлером, сравнение с `ad7e2da039`, Затон, ясная погода, медиана по 6 прогонам:

| Показатель, мс | До | После |
| --- | --- | --- |
| Ожидание старта каскадов | 0,268 | 0 |
| `Collect Sun Cascades` | 0,396 | 0,116 |
| Кадр целиком | 2,297 (разброс 2,21–2,56) | 2,258 (разброс 2,22–2,33) |

Простой воркера исчез, сама сборка не подорожала. Кадр на этой лёгкой сцене не изменился в пределах разброса: join и раньше почти не ждал. Покрытие теней: при скачке камеры 0,2 рад за кадр разница в пределах шума; при 1 рад за кадр дыр нет, отличаются кусты вблизи камеры. Не проверено: тяжёлая сцена, режим редактора (`xrECore` на ветке не собирается).

**Готово, когда:** на профайлере нет простоя в `Collect Sun Cascades`, тени совпадают с эталоном на статичной камере и не теряют покрытие при резком повороте. Картинка в движении может отличаться на кадр.

### Этап 3. Единая сборка: `Begin` и `CollectGraphs`

Заменить ручную настройку и тикеты каскадов и отражений одним запуском. `render_subspace` разбить на `Traverse`, `CollectDynamic`, `CaptureStatic`, `CaptureDynamic`, а старые перегрузки оставить обёртками до этапа 6. `append_sun_dynamics` использует уже готовый обход, а не делает новый.

**Готово, когда:** каскады и отражения описаны только через `GraphView`, порталы для каскада обходятся один раз за кадр.

### Этап 4. Дождь как проверка унификации

`GraphRain`: разделить `render_rain` на расчёт матриц до старта воркера и отрисовку, сборка идёт через `CollectGraphs`. Это самый простой вид и проверка цели: добавить проход должно быть почти только новым описанием.

**Готово, когда:** дождь не трогает `GraphMain`, собирается на воркере, правки сборочного кода не понадобились.

### Этап 5. Остальные проходы и один режим

`GraphShadow` для прожекторов, `decor_object` и кэша теней. `GraphZPrefill`. Статическое освещение (`r1_LightPPA.cpp`) механически, через свой граф.

После этого неизолированного режима больше нет, и можно удалить:

- `own_clips` как режим: клипы всегда у графа.
- `CSector::r_frustums`, `r_marker`, `r_scissors`, покадровые поля `CPortal`, `VQ_SCISSOR`.
- Подмену `ViewBase`.

Потребители `r_marker` (`Light_DB.cpp:224`, `light.cpp:228`, `DetailManager.cpp:218`, `DetailManager_Render.cpp:356`) переходят на `GraphMain.IsSectorVisible`. Сейчас тени перезаписывают обход `GraphMain`, после этапа ответ всегда будет про основную камеру. Это изменение поведения, его надо проверить отдельно.

Дедупликацию свести к одному механизму: для статики битовый массив на граф по индексу визуала, для динамики `private_visuals`. Общий `marker` и `light_smapvis` перевести или убрать. `add_static` — самая тяжёлая зона на профайлере, поэтому цену `private_visuals` (хэш на каждый лист) замерить отдельно.

**Готово, когда:** ни один проход, кроме основного, не пишет в `GraphMain`.

### Этап 6. Основная сцена как обычный вид, один сбор на кадр

`render_main` превращается в `Begin` + `Traverse` + `Capture*`. Сбор сразу включает приоритеты 0 и 1 и wallmarks, поэтому `render_forward` больше не обходит сцену (`r4_R_render.cpp:879`). Частицы собираются отдельно перед forward, HUD один раз. `mapHUDScopeMask` должен быть известен до решения о `split_the_scene`. Вставка Distort зависит от `distortion_enabled`. Убрать обёртки `r_dsgraph_render_subspace`.

Это самый рискованный этап: два вызова `render_main` с разными масками держат много неявных зависимостей. Переносить по одной и сверять draw call.

**Готово, когда:** один обход на кадр, картинка совпадает с эталоном, `RenderCALC` упал.

### Этап 7. Раздельная и стабильная статика

`r_dsgraph_render_static`, `r_dsgraph_render_dynamic`, `ClearStatic`, `ClearDynamic`. Отрисовка с `Clear=false` не должна менять граф, чтобы граф можно было использовать повторно. Sorted-списки не делить: статика и динамика сортируются вместе.

Стабильный граф хранится в `SpotShadowCacheEntry`, где уже есть лимит памяти и классификация. В него идёт только фиксированная геометрия, собирается без камерных фильтров. Группы `MT_MESH_LODS` и `MT_LOD` остаются покадровыми: выбор лода зависит от камеры. Инвалидация: движение света, смена сектора, загрузка уровня, сброс устройства, ревизии текстур и шейдеров. По замерам решить, нужен ли ещё `smapvis`. Каскады — так же, если замер покажет выигрыш.

**Готово, когда:** на статичном свете нет повторного обхода, тени верны при движении камеры и на переходах лодов.

### Этап 8 (необязательный). Больше работы на воркерах

Можно распараллелить `CaptureStatic` основной сцены и теней прожекторов. Для динамики на воркере сначала решить открытый вопрос из раздела 4. Проверить `renderable_Render` на чистоту: `CalculateWallmarks`, `CROS_impl::update`, `hom_frame`, `Skinning.Request`, `Lights.add_light`, `L_Shadows`. Отрисовка остаётся на основном потоке.

**Готово, когда:** чистый прогон под `IXRAY_ASAN` и измеримый выигрыш. Без выигрыша этап не вливается.

## 7. Проверка

Автотест из `docs/engine/lifecycle.md` и ручные сценарии с фиксированной камерой:

- Порталы: на пороге, через несколько секторов, подземелья, `rs_render_portals`.
- Порядок и прозрачность: sorted, Distort, emissive, wallmarks, частицы, в том числе HUD.
- HUD и прицелы: `mapHUDScopeMask`, HUD-свет, 3D-иконки.
- Свет: омни с тенью, `decor_object`, `ignore_object`, `r4_spot_shadow_cache` 0–2, `r4_sun_shadow_cache` 0–2.
- Каскады в движении: резкий поворот, телепорт, смена уровня.
- Лоды: переходы `MT_MESH_LODS`, билборды, тени в момент перехода.
- Режимы: статическое освещение, редактор, `R2FLAG_ZFILL`, `R2FLAG_EXP_SPLIT_SCENE`, `r__mt_skeletons off`.
- Жизненный цикл: сброс устройства, смена уровня, сейв/лоад, уничтожение объекта во время сборки. Для последнего — `IXRAY_ASAN`.

## 8. Вне плана

Из образца не переносятся асинхронная загрузка cform, `Feel_Vision` и правки AI: к графу они не относятся. Отдельная база света `g_SpatialSpaceLights` — независимая оптимизация, её можно рассмотреть после этапа 5.
